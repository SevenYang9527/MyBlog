SOLID 原则

在投身于模式本身之前，我们先来看看一些会影响它们运作方式的设计原则。

SOLID 是软件设计五项核心基础的首字母助记缩写（mnemonic acronym）：

  • 单一职责（Single Responsibility）
  • 开闭（Open-Closed）
  • 里氏替换（Liskov Substitution）
  • 接口隔离（Interface Segregation）
  • 依赖倒置（Dependency Inversion）

让我们逐一考察每个概念，看看它们如何帮助你让代码更易理解、更灵活、更易维护。

单一职责原则（Single-Responsibility Principle）

一个类应该只有一个引起它变化的原因，那就是它唯一的职责。

第一条也是最重要的 SOLID 原则是单一职责原则（Single-Responsibility Principle，SRP），它指出每个模块、类或函数只负责一件事，并且只封装那部分逻辑。

用许多更小的部分来组装你的项目，而不是构建单体式（monolithic）的巨型类。更短的类和方法更容易讲解、理解和实现。

如果你在 Unity 中工作过一段时间，很可能已经熟悉这个概念了。当你创建一个 GameObject 时，它持有一系列更小的组件。例如，它可能包含：

  • 一个 MeshFilter，用于存储对 3D 模型的引用
  • 一个 Renderer，用于控制模型表面在屏幕上的呈现方式
  • 一个 Transform 组件，用于存储缩放、旋转和位置
  • 如果它需要参与物理模拟，则还有一个 Rigidbody

每个组件只做一件事，并且把它做好。你用 GameObject 构建出整个场景。正是各组件之间的交互，才让游戏成为可能。

你也会以同样的方式构造自己编写的脚本组件。设计它们时，要让每一个都能被清晰地理解。然后让它们协同工作，从而实现复杂的行为。

如果你忽视单一职责，可能会写出这样一个自定义组件：

一个承担多项职责的 Player 脚本

public class UnrefactoredPlayer : MonoBehaviour
{
    [SerializeField] private string inputAxisName;
    [SerializeField] private float positionMultiplier;
    private float yPosition;
    private AudioSource bounceSfx;
    private void Start()
    {
        bounceSfx = GetComponent<AudioSource>();
    }
    private void Update()
    {
        float delta = Input.GetAxis(inputAxisName) * Time.deltaTime;
        yPosition = Mathf.Clamp(yPosition + delta, -1, 1);
        transform.position = new Vector3(transform.position.x, yPosition * positionMultiplier, transform.position.z);
    }
    private void OnTriggerEnter(Collider other)
    {
        bounceSfx.Play();
    }
}

这个 UnrefactoredPlayer 类把各种职责混在了一起。它在玩家与某物碰撞时播放音效、管理输入，还处理移动。即使这个类目前还相对较短，但随着项目不断演进，它会变得越来越难以维护。可以考虑把 Player 类拆分成更小的类。

重构后的 Player，被拆分为多个单一职责的类

Player 脚本仍然可以管理其他脚本组件，但每个类只做一件事。这种设计让修改代码变得更平易，尤其是当项目需求随时间变化时。

但另一方面，你需要用足够的常识来平衡单一职责原则。不要走到另一个极端，创建只有一个方法的类。

在应用单一职责原则时，请牢记以下目标：

  • 可读性（Readability）：短小的类更易读。这一点没有硬性规定，但许多开发者把上限设在 200–300 行。你可以自己或与团队一起确定什么算「短」。一旦超过这个阈值，就判断能否把它重构为更小的部分。
  • 可扩展性（Extensibility）：你可以更轻松地从小的类继承。修改或替换它们时，不必担心破坏意料之外的功能。
  • 可复用性（Reusability）：把类设计得小而模块化，这样你就能在游戏的其他部分复用它们。

重构时，请考虑重新组织代码将如何改善你自己或其他团队成员的工作体验。前期多花一点功夫，日后能为你省下很多麻烦。

简单并不等于容易

在软件设计中，简单性（simplicity）经常被谈及，它是可靠性的前提。你的软件设计能否应对生产环境中的变化？你能否随时间推移扩展并维护你的应用？

本指南介绍的许多设计模式和原则都能帮助你落实简单性。它们借此让你的代码更具可扩展性、更灵活、更易读。不过，它们也需要一些额外的工作和规划。「简单」并不等同于「容易」。

尽管不用这些模式也能实现相同的功能（而且往往更快），但快速、容易做出来的东西未必就是简单的。让某样东西变简单，意味着让它专注。把它设计成只做一件事，不要用其他任务把它复杂化。

可以看看 Rich Hickey 的讲座《Simple Made Easy》，理解简单性如何帮助你构建更好的软件。

开闭原则（Open-Closed Principle）

SOLID 设计中的开闭原则（Open-Closed Principle，OCP）认为，类必须对扩展开放、对修改关闭。这样来组织你的类：你可以在不修改原始代码的前提下创建新的行为。

一个经典的例子是计算形状的面积。你可以创建一个名为 AreaCalculator 的类，其中的方法分别返回矩形和圆形的面积。

就计算面积而言，Rectangle 类有 Width 和 Height。Circle 只需要 Radius 和圆周率的值。

public class AreaCalculator 
{
    public float GetRectangleArea(Rectangle rectangle)
    {
        return rectangle.width * rectangle.height;
    }
    public float GetCircleArea(Circle circle)
    {
        return circle.radius * circle.radius * Mathf.PI;
    }
}
public class Rectangle
{
     public float width;
     public float height;
}
public class Circle
{
    public float radius;
}

这样已经够用了，但如果你想给 AreaCalculator 增加更多形状，就得为每个新形状创建一个新方法。假设你之后想传入一个五边形或八边形呢？如果你需要再加 20 种形状呢？AreaCalculator 类会迅速膨胀到失控。

你可以创建一个名为 Shape 的基类，并编写一个方法来处理这些形状。但这样做需要在逻辑内部使用多个 if 语句来处理每种形状。那不具备良好的可扩展性。

你希望让程序对扩展开放（能够使用新形状），同时不修改原始代码（AreaCalculator 的内部实现）。尽管当前的 AreaCalculator 能正常工作，但它违反了开闭原则。

我们该如何设计 AreaCalculator，使它能够接收新的形状？

取而代之，可以考虑定义一个抽象的 Shape 类：

public abstract class Shape
{
    public abstract float CalculateArea();
}
public class Rectangle : Shape
{
    public float width;
    public float height;
    public override float CalculateArea()
    {
        return width * height;
    }
}
public class Circle : Shape
{
    public float radius;
    public override float CalculateArea()
    {
        return radius * radius * Mathf.PI;   
    }
}

其中包含一个名为 CalculateArea 的抽象方法。如果你让 Rectangle 和 Circle 继承 Shape，那么每种形状都能计算自己的面积，并返回如下结果：

AreaCalculator 可以简化为这样：

public class AreaCalculator 
{
    public float GetArea(Shape shape)
    {
        return shape.CalculateArea();
    }
}

按照开闭原则修订各个类

修改后的 AreaCalculator 类现在可以获取任何正确实现了抽象 Shape 类的形状的面积。这样你就能扩展 AreaCalculator 的功能，而无需改动它的任何原始源代码。

每当你需要一个新的多边形时，只需定义一个继承自 Shape 的新类。每个子类形状随后重写 CalculateArea 方法，以返回正确的面积。

这种新设计让调试更轻松。如果新增的形状引入了错误，你不必回头检查 AreaCalculator。旧代码保持不变，所以你只需要检查新代码中是否存在错误逻辑。

在 Unity 中创建新类时，善用接口（interface）和抽象（abstraction）。这有助于避免逻辑中出现日后难以扩展的笨重 switch 或 if 语句。一旦你习惯了让自己的类遵循 OCP，从长远来看添加新代码就会变得更简单。

里氏替换原则（Liskov Substitution Principle）

里氏替换原则（Liskov Substitution Principle，LSP）指出，派生类必须能够替换其基类。面向对象编程中的继承让你可以通过子类添加功能。不过，稍不留意，这也可能带来不必要的复杂性。

作为 SOLID 的第三根支柱，里氏替换原则告诉你如何应用继承，让你的子类更健壮、更灵活。

设想你的游戏需要一个名为 Vehicle 的类。它将是你为应用创建的载具子类的基类。例如，你可能需要一辆汽车或一辆卡车。

一切都继承自 Vehicle。

凡是能使用基类（Vehicle）的地方，你都应该能够使用 Car 或 Truck 这样的子类，而不会破坏应用。
