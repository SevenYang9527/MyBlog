第 4 章 正确收发数据流：粘包、半包与分帧

TCP 是字节流，不保留消息边界：你发两次 100 字节，接收端可能一次收到 200 字节（粘包），也可能先收到 50 字节（半包）。这不是“TCP 的 bug”，而是流式协议的正常行为。应用层必须自己分帧。

常见分帧方案：长度前缀（先读 4 字节长度，再读 payload）、固定长度、分隔符。长度前缀最通用；要注意大小端（网络序通常大端）、长度上限、恶意超长包。发送端还可能“没发完”（Send 返回值小于请求），接收端要循环读到足够字节。

这一章的核心是“把字节流还原成消息”：缓冲区、队列、循环读、长度校验、线程安全。

关键实现：4 字节长度前缀

发送端先写 4 字节大端长度，再写 payload；接收端先读满 4 字节，再读满 length 字节。长度要有上限，防止恶意包把内存打爆。

static async Task SendFrame(NetworkStream stream, byte[] payload, CancellationToken ct)
{
    var header = new byte[4];
    BinaryPrimitives.WriteInt32BigEndian(header, payload.Length);
    await stream.WriteAsync(header, ct);
    await stream.WriteAsync(payload, ct);
}

static async Task<byte[]> ReadFrame(NetworkStream stream, CancellationToken ct)
{
    var header = new byte[4];
    await stream.ReadExactlyAsync(header, ct); // .NET 7+
    int len = BinaryPrimitives.ReadInt32BigEndian(header);
    if (len <= 0 || len > 1024 * 1024) throw new InvalidDataException("bad length");
    var payload = new byte[len];
    await stream.ReadExactlyAsync(payload, ct);
    return payload;
}

常见坑

  • 用 BitConverter 不统一端序；跨平台/跨语言时高低字节反了。
  • Send 一次就认为发完；实际可能只发了一部分。
  • 接收端每次 Read 就当一条消息；粘包/半包直接解析错。
  • 多线程同时读写同一个 ByteArray/Queue；需要锁或单线程消费。

练习

写一个随机拆分字节流的测试：把一条完整帧随机切成 1~N 段喂给接收端，验证仍能还原；再加 10MB 上限和超长包日志。

2026 更新：现代 .NET 用 System.IO.Pipelines、ReadOnlySequence<byte>、Span<byte>、ArrayPool、BinaryPrimitives 降低分配；NetworkStream.ReadExactly（.NET 7+）简化“读满”。WebSocket 自带消息帧，但仍要校验长度/类型。

本章要点：TCP 是字节流，粘包/半包正常；应用层分帧：长度前缀/固定长度/分隔符；处理大小端、长度上限、发送不完整、循环读；线程安全队列。
