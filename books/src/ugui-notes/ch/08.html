合批：先算层级，再按层级贪心合并

讲义第 23 页给出了 UGUI 合批的两步：先做重叠检测、计算每个元素的“层级号”，再把同一层级里能合的元素合并成批次，最后把批次数据放进 CanvasMesh 的 SubMesh。这个描述大方向是对的，而且比很多“同图集就能合批”的说法准确得多。本章把算法补完整，并解释为什么“同图集”仍然可能不合。

合批的基本单位是 Canvas

一个 Canvas 会收集它下面、但不属于任何 Sub-canvas 的 CanvasRenderer。这些 Renderer 带着各自的网格、材质、纹理、裁剪信息和层级深度，进入批次构建。构建的目标是：在不改变绘制结果的前提下，把能一起画的元素合并成尽量少的批次。

一个批次通常对应一个材质/纹理组合，最终通常是一个 SubMesh / 一次 DrawCall；具体取决于材质和 SubMesh 的组织方式。一个 Canvas 生成一个组合 Mesh，但里面可以有多个 SubMesh；所以“一个 Canvas 一个 Mesh”和“一个 Canvas 多个 DrawCall”可以同时成立。

层级号（Depth）怎么算

把 Canvas 下的可绘制元素按 Hierarchy 顺序（深度优先）排好，然后从前往后处理。对当前元素 Current：

  1. 找出所有在它“下面”、并且和它矩形相交的元素。
  2. 如果没有相交元素，Current.depth = 0。
  3. 如果有相交元素，取这些元素里的最高深度 MaxLowerDepth：
    • 如果 Current 能和最高深度上的元素合批，并且最高深度上只有一个“可合批候选”，则 Current.depth = MaxLowerDepth。
    • 否则 Current.depth = MaxLowerDepth + 1。
  4. 如果元素不共面（有 Z 偏移、旋转）、或者带 CanvasGroup 的注入索引等特殊情况，它可能被迫独占一个深度/批次。

讲义把规则概括成“如果底下有一个能合批的，就同级；不能合批就 +1；有多个就取最大”。这个概括在多数情况下够用，但漏掉了“最高深度上有多个元素且不能全部合批”的细节。真正的实现还要考虑材质、纹理、裁剪、A8 纹理格式、是否共面等条件。

排序与合并

算完深度后，元素会按“深度 → 材质 → 纹理 → 渲染顺序”排序。然后从头到尾贪心地合并：相邻且满足合批条件的元素进入同一个批次；一旦遇到不能合的元素，批次就断开，后面的元素即使条件满足也回不到前面的批次。这就是为什么“中间插一个不同图集的元素”代价很大。

// 概念上的排序键（不同版本细节略有差异）
// depth 小的先画；同 depth 按材质、纹理、renderOrder 排
if (a.depth != b.depth) return a.depth.CompareTo(b.depth);
if (a.materialId != b.materialId) return a.materialId.CompareTo(b.materialId);
if (a.textureId != b.textureId) return a.textureId.CompareTo(b.textureId);
return a.renderOrder.CompareTo(b.renderOrder);

为什么同图集也可能不合批

讲义第 27 页讲“Hierarchy 穿插重叠问题”：红点和 Icon 如果在不同图集里，红点稍微大一点、遮住了旁边的 Icon，就不能合批。这个例子说明了一个关键点：合批不是“全局找同图集”，而是“按绘制顺序，在不破坏遮挡关系的前提下合并”。

常见的合批打断原因

打断原因典型场景处理方向
不同纹理 / 图集图标来自不同 Sprite Atlas，或未打图集把同一界面的图放进同一图集；避免在一个批次中间穿插另一图集的元素。
不同材质实例自定义 Shader、不同的 Material Preset、字体材质不同共享材质；把使用同一材质的元素放在一起；TMP 字体尽量用同一 Font Asset / Material Preset。
Mask / RectMask2DScrollView、圆形头像、异形裁剪矩形裁剪优先 RectMask2D；减少嵌套 Mask；Mask 的 stencil 状态会打断批次。
不共面元素有 Z 偏移、旋转、缩放（非 Canvas 平面）可合批的元素保持 Z=0、无旋转；需要旋转的元素单独组织。
CanvasGroup用 CanvasGroup 做淡入淡出、弹窗遮罩CanvasGroup 会产生 CanvasInjectionIndex，可能强制新批次；不要给每个元素都挂 CanvasGroup。
空 Image用空 Image 做点击热区空 Image 会画白色 quad，纹理是白图，打断合批；换成不绘制的 Raycast Graphic。

注意：合批优化的是 DrawCall 数量，不是 像素填充量。一个大面积半透明图片即使和其他元素合批，Overdraw 仍然存在；反之，减少 Overdraw 也不一定减少 DrawCall。两个问题要分开看。

考据结论：讲义第 23 页的两步合批模型基本正确，但“层级号”规则需要按“最高相交深度 + 是否能合批”补完整；“同一层级可以合批”是启发式，不是保证。最终数据放在 CanvasMesh 的 SubMesh 里是对的，但一个 Canvas 可能产生多个 SubMesh / DrawCall。

怎么验证

不要靠猜。打开 Frame Debugger，找到 UI 的绘制事件，看每个批次包含哪些 GameObject；或者用 Profiler 的 UI / UI Details 模块，看 Self Batch Count、Cumulative Batch Count 和 Batch Breaking Reason。常见原因会直接写出来，例如：

  • Not Coplanar With Canvas：元素不共面。
  • CanvasInjectionIndex：CanvasGroup 等注入了新的批次。
  • Different Material Instance、Different Texture、Different Rect Clipping、Different A8TextureUsage：材质、纹理、裁剪或 A8 纹理格式不同。

先让工具告诉你“为什么断”，再决定是换图集、调层级，还是拆 Canvas。盲目把 UI 拆成很多 Canvas，可能只是把一次大批次换成很多小批次，DrawCall 反而更多。

一个实用的组织原则

把“会一起出现、会互相遮挡、且使用同一图集/材质”的元素放在相邻的层级位置；把“中间会插进来”的不同图集元素移到它们的前面或后面；把“独立更新”的模块拆到子 Canvas。这个原则比“相同层级原则”更接近实际：层级只是手段，遮挡关系和材质一致性才是目的。
