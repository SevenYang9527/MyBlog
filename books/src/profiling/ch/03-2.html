找出瓶颈

在某些平台上，判断你的应用是受限于 CPU 还是 GPU（CPU-bound 或 GPU-bound）很容易。例如，在 Xcode 中运行 iOS 游戏时，fps 面板会显示一个条形图，其中包含 CPU 和 GPU 的总耗时，你可以据此看出哪一个更高。需要注意的是，CPU 耗时包含等待 VSync（垂直同步）所花的时间，而 VSync 在移动设备上始终是启用的。

然而，在某些平台上获取 GPU 计时数据可能很困难。所幸 Unity Profiler 提供的信息已足以定位性能瓶颈所在。下面的流程图展示了最初的性能分析（profiling）流程，其后的各节则详细说明每一个步骤。这些小节还会展示来自真实 Unity 项目的 Profiler 捕获数据，用以说明应该留意哪些情况。

什么是 VSync？

VSync 会让应用的帧率与显示器的刷新率同步。这意味着，如果你使用 60Hz 显示器，而游戏能在 16.66 ms 的帧预算（frame budget）之内运行，它就会被强制以 60 fps 运行，而不是被允许跑得更快。把 fps 与显示器的刷新率同步可以减轻 GPU 的负担，并避免画面撕裂（screen tearing）之类的视觉瑕疵。在 Unity 中，你可以在 Quality 设置（Edit > Project Settings > Quality）里把 VSync Count 配置为一项属性。

按照下面的流程图，并借助 Profiler 来帮助确定应该把优化精力集中在何处：

要全面了解所有的 CPU 活动（包括 CPU 在等待 GPU 时的时段），请使用 Profiler 的 CPU Usage 模块中的 Timeline 视图。熟悉常见的 Profiler 标记（Profiler marker），才能正确解读捕获数据。部分 Profiler 标记在不同目标平台上可能呈现出不同的样子，因此请花些时间查看游戏在各个目标平台上的捕获数据，感受一下你的项目「正常」的捕获数据是什么样子。

一个项目的性能受限于耗时最长的那个芯片和/或线程。那才是优化工作应该聚焦的地方。例如，设想一个游戏的目标帧时间预算为 33.33 ms，并且启用了 VSync：

  • 如果 CPU 帧时间（不含 VSync）为 25 ms、GPU 时间为 20 ms，那没有问题！你受限于 CPU，但一切都在预算之内，此时做优化并不会提升帧率（除非你把 CPU 和 GPU 都降到 16.66 ms 以下，从而跃升到 60 fps）。
  • 如果 CPU 帧时间为 40 ms、GPU 为 20 ms，你受限于 CPU，需要优化 CPU 性能。此时优化 GPU 性能不会有帮助；事实上，你可能想把一部分 CPU 工作转移到 GPU 上，例如对某些内容改用 Compute shader（计算着色器）而不是 C# 代码，从而让两者更均衡。
  • 如果 CPU 帧时间为 20 ms、GPU 为 40 ms，你受限于 GPU，需要优化 GPU 的工作。
  • 如果 CPU 和 GPU 都处于 40 ms，你同时受两者限制，需要把两者都优化到 33.33 ms 以下，才能达到 30 fps。

你是否在帧预算之内？

在整个开发过程中尽早且频繁地对项目进行分析与优化，可以帮助你确保应用的所有 CPU 线程以及整体的 GPU 帧时间都处于帧预算之内。

下图是一张性能分析捕获数据的截图，它来自一个由坚持持续分析与优化的团队所开发的 Unity 移动游戏。该游戏在高配手机上以 60 fps 为目标，在中低配手机（例如本次捕获所用的设备）上以 30 fps 为目标。

请注意，所选帧上几乎一半的时间都被黄色的 WaitForTargetfps Profiler 标记占据。该应用已将 Application.targetFrameRate 设为 30 fps，并且启用了 VSync。主线程上实际的处理工作在大约 19 ms 处就结束了，其余时间都在等待 33.33 ms 中剩下的部分过去，然后才开始下一帧。虽然这段时间由一个 Profiler 标记表示，但主 CPU 线程在此期间基本处于空闲状态，从而让 CPU 得以降温，并且只消耗最低限度的电量。

在其他平台上，或者在禁用 VSync 的情况下，需要留意的标记可能不同。关键在于检查主线程是在帧预算之内运行，还是恰好贴着帧预算运行、并带有某种表明应用正在等待 VSync 的标记，以及其他线程是否拥有空闲时间。

空闲时间由灰色或黄色的 Profiler 标记表示。上图显示渲染线程正空闲在 Gfx.WaitForGfxCommandsFromMainThread 中，这表示它已经在某一帧把绘制调用（draw call）发送给 GPU，正在等待下一帧来自 CPU 的更多绘制调用请求。同样地，尽管 Job Worker 0 线程有一部分时间花在 Canvas.GeometryJob 上，但大部分时间都处于 Idle。这些都是应用轻松处于帧预算之内的迹象。

如果你的游戏在帧预算之内

如果你处于帧预算之内——包括为考虑电量消耗与热降频而对预算所做的任何调整——那么在下一次需要做性能分析之前，你已经完成了本次性能分析工作，恭喜。可以考虑运行 Memory Profiler，以确保应用同样处于其内存预算之内。

受限于 CPU

如果你的游戏不在 CPU 帧预算之内，下一步就是调查 CPU 的哪一部分是瓶颈——换句话说，哪个线程最忙。性能分析的目的是找出瓶颈并将其作为优化目标；如果只靠猜测，你可能最终优化了游戏中并非瓶颈的部分，结果整体性能几乎没有改善，甚至毫无改善。有些「优化」甚至可能让游戏的整体性能变得更糟。

整个 CPU 负载成为瓶颈的情况很少见。现代 CPU 拥有多个不同的核心，能够独立且同时执行工作。不同的线程可以运行在各个 CPU 核心上。一个完整的 Unity 应用会为不同目的使用一系列线程，但在排查性能问题时最常见的线程是以下几个：

  • 主线程：默认情况下，所有游戏逻辑/脚本都在这里执行，而物理、动画、UI 和渲染等功能与系统的大部分时间也花在这里。
  • 渲染线程：在渲染过程中，主线程会检查场景并执行相机剔除（Camera culling）、深度排序和绘制调用批处理（draw call batching），从而得到一份待渲染内容列表。这份列表被传递给渲染线程，渲染线程再把它从 Unity 内部与平台无关的表示形式，转换为在特定平台上指示 GPU 所需的特定图形 API 调用。
  • Job 工作线程：开发者可以利用 C# Job System 把某些类型的工作调度到工作线程上运行，从而减轻主线程的负载。Unity 的一些系统和功能也会用到 Job System，例如物理、动画和渲染。

主线程

下图展示了受限于主线程的项目大致会是什么样子。这个项目运行在 Meta Quest 2 上，该设备通常以 13.88 ms（72 fps）甚至 8.33 ms（120 fps）的帧预算为目标，因为高帧率对于避免 VR 设备中的晕动症很重要。然而，即便这款游戏以 30 fps 为目标，也很明显这个项目遇到了麻烦。

尽管渲染线程和工作线程看起来与那个处于帧预算之内的示例相似，但主线程显然在整个帧期间都忙于工作。即便把帧末尾少量的 Profiler 额外开销计算在内，主线程也忙了超过 45 ms，这意味着该项目只能达到低于 22 fps 的帧率。没有任何标记显示主线程在空闲地等待 VSync；它整帧都在忙。

下一阶段的调查是找出帧中耗时最长的部分，并理解其中的原因。在这一帧上，PostLateUpdate.FinishFrameRendering 耗时 16.23 ms，超过了整个帧预算。进一步查看会发现，有一个名为 Inl_RenderCameraStack 的标记出现了五次，说明有五个相机处于激活状态并在渲染场景。由于 Unity 中的每个相机都会调用完整的渲染管线（包括剔除、排序和批处理），这个项目最优先的任务就是减少激活相机的数量，理想情况下只保留一个。

BehaviourUpdate 这个涵盖所有 MonoBehaviour Update() 方法的标记耗时 7.27 ms，而时间轴上的品红色区段表示脚本在何处分配托管堆（managed heap）内存。切换到 Hierarchy 视图并在搜索栏中输入 GC.Alloc 进行筛选，可以看到这一帧中分配这些内存大约耗时 0.33 ms。然而，对于内存分配给 CPU 性能带来的影响而言，这是一个不准确的度量。

GC.Alloc 标记实际上并不是通过测量从 Begin 到 End 的时间来计时的。为了保持低开销，它们只记录 Begin 时间戳，以及其分配的大小。Profiler 会给它们分配一个最小的时间量，以确保它们可见。实际分配可能耗时更长，特别是在需要向系统申请一段新的内存时。要更清楚地看出这种影响，请在其周围放置 Profiler 标记。
