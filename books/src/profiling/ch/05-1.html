Unity 性能分析与调试工具（Unity Profiling & Debug Tools）

本节将深入介绍 Unity 中每一种性能分析与调试工具的能力。

关于工具差异的说明

本节提到的一些工具其实属于其他类别，例如调试工具，帧调试器（Frame Debugger）就是一个例子。严格来说它们并不是性能分析器（profiler），但在分析和改进 Unity 项目时，把它们纳入你的工具箱是很重要的。

以下是性能分析工具、调试工具与静态分析工具之间的区别。

  • 性能分析工具通过插桩（instrumentation）来收集与代码执行相关的耗时数据。
  • 调试工具允许你单步执行程序、暂停并查看变量的值，并提供许多其他高级功能。例如，帧调试器让你可以逐条遍历一帧的渲染过程、查看着色器（shader）中的值等等。
  • 静态分析器（static analyzers）是一类程序，它以源代码或其他资源作为输入，用内置规则进行分析，从而推断该输入是否“正确”，并且无需运行项目。

性能分析器（Profiler）

Unity 性能分析器可帮助你定位运行时任何瓶颈或卡顿的成因，并更好地理解在某一帧或某个具体时间点究竟发生了什么。

Unity 中的性能分析基于插桩，因此你会得到大量可供分析的性能分析器标记（Profiler marker）数据。请注意，直接在编辑器中进行性能分析会带来一定开销，并可能使结果失真。同样地，你的开发机很可能比目标设备强大得多。

只启用你确实需要使用的性能分析器模块，或者改用独立性能分析器（Standalone Profiler），后者能带来更干净的性能分析数据和更低的性能分析开销等好处。

作为一般经验法则，始终启用 CPU、Memory 和 Renderer 模块是很有用的。其他模块，例如 Audio 和 Physics，则按需启用。

Unity 性能分析入门

按照以下步骤开始使用 Unity 性能分析器：

  • 进行性能分析时必须使用开发构建（Development Build）。通过 File > Build Settings > 勾选 Development Build 来完成。
  • 勾选 Autoconnect Profiler 复选框（此项为可选）。
  • 注意：Autoconnect Profiler 会让首次启动时间增加最多 10 秒，因此只有在你想要分析第一个场景的初始化过程时才应启用它。如果你没有启用 Autoconnect Profiler，你随时可以手动把性能分析器连接到正在运行的开发构建上。
  • 为目标平台执行构建。
  • 通过 Window > Analysis > Profiler 打开 Unity 性能分析器。
  • 禁用你不需要的性能分析器模块。每启用一个模块都会给播放器（player）带来性能开销。（你可以借助 Profiler.CollectGlobalStats 标记观察到其中一部分开销。）
  • 关闭设备的移动网络，保持 WiFi 开启。
  • 在目标设备上运行该构建。
  • 如果你勾选了 Autoconnect Profiler，那么构建中会预先写入编辑器所在机器的 IP 地址。应用启动时，会尝试直接连接该 IP 地址上的 Unity 性能分析器。性能分析器将自动连接并开始显示帧信息和性能分析信息。
  • 如果你没有勾选 Autoconnect Profiler，则需要通过 Target Selection 下拉菜单手动连接到你的播放器（Player）。

为了节省构建时间（代价是精度降低），你也可以直接对运行在 Unity 编辑器中的应用程序做性能分析。在性能分析器窗口的 Attach to Player 下拉菜单中选择 Playmode。

性能分析器使用技巧

在 CPU Usage 性能分析器模块中禁用 VSync 与 Others 类别

垂直同步（VSync）标记代表“死时间”，即 CPU 主线程在等待 VSync 时处于空闲状态。隐藏标记有时会让你难以理解其他类别的耗时是如何形成的，甚至难以理解总帧时间是如何构成的。考虑到这一点，另一种选择是重新排列列表，让 VSync 位于最上方。这样图表的视图会更清晰，VSync 标记带来的“噪声”被减少，整体情况一目了然。

Others 标记代表性能分析本身带来的开销，可以放心忽略，因为它不会出现在项目的最终构建中。

在构建中禁用 VSync

另一个看清主线程、渲染线程与 GPU 如何交互的办法，是对一个完全禁用 VSync 的构建做性能分析。依次进入 Edit > Project Settings…，然后选择 Quality，点击目标设备上将使用的 Quality Level(s)，并把 VSync Count 设为 Don’t Sync。制作一个游戏的开发构建，然后把性能分析器连接到它。这样游戏不再等待下一个垂直消隐（VBlank），而是一帧结束后立即开始下一帧。在某些平台上，禁用 VSync 可能导致画面撕裂等视觉瑕疵（若是如此，记得在发布构建中重新启用它），但去掉这段人为的等待能让性能分析器的采集结果更易读懂，尤其是在排查项目中的瓶颈所在时。

知道何时在 Playmode 或编辑器模式下做性能分析

使用性能分析器时，你可以选择 Playmode、Editor，或者远程/已连接设备作为播放器目标。

用 Playmode 来分析你的游戏/应用程序，用 Editor 模式来查看承载游戏的 Unity 编辑器自身在做什么。

把 Editor 作为性能分析目标会严重影响性能分析的准确性。此时性能分析器窗口实际上是在递归地分析它自己。不过，如果编辑器的性能变慢，对编辑器做性能分析也是有价值的。这样你就能找出拖慢编辑器、影响工作效率的脚本和扩展。

以下是一些你可能需要分析编辑器的情形：

  • 按下 Play 按钮后，进入播放模式需要很长时间
  • 编辑器变得迟钝、无响应
  • 项目打开需要很长时间。博客文章《Tips for working more effectively with the Asset Database》介绍了如何使用 -profiler-enable 命令行选项，从编辑器启动的那一刻就开始性能分析。

使用独立性能分析器

请使用独立性能分析器。当你想要进行播放模式或编辑器模式下的性能分析时，性能分析器会作为独立于 Unity 编辑器的新进程启动。这样就避免了性能分析器界面或编辑器本身影响所测得的耗时数据。你还会得到一组更干净、便于筛选和分析的性能分析数据。

在编辑器中进行性能分析以实现快速迭代

当你想要快速迭代解决性能问题时，就在编辑器中做性能分析。例如，如果在构建版本中发现了性能问题，先在编辑器中做性能分析，确认你在那里也能复现它。如果你确实找到了问题，就利用播放模式下的性能分析，快速迭代尝试可能的解决方案。问题解决后，制作一个构建版本，并验证该方案在目标设备上同样有效。

这套工作流程之所以最优，是因为你在构建改动和部署到设备上花费的时间更少。相反，你可以在编辑器中快速迭代，并用性能分析工具验证改动结果。

帧调试器（Frame Debugger）

帧调试器通过让你把正在运行的游戏冻结在某一特定帧，并查看用于渲染该帧的各个绘制调用（draw call），来帮助你优化渲染。该工具让你可以逐条遍历绘制调用列表，从而看到这些帧是如何由各种图形元素一步步构建成一个场景的。

与其他帧调试工具相比，帧调试器的一个优势是：当某条绘制调用对应某个 GameObject 的几何体时，该对象会在主 Hierarchy 面板中被高亮显示，便于识别。

帧调试器还可用于逐帧分析渲染顺序，从而检测过度绘制（overdraw）。更多信息请参阅下面的优化技巧。

从 Window > Analysis > Frame Debugger 菜单打开帧调试器。在应用程序运行于编辑器或设备上的情况下，点击 Enable。这会暂停应用程序，并在 Frame Debug 窗口左侧按顺序列出当前帧的所有绘制调用。诸如帧缓冲清除事件之类的额外细节也会一并列出。

调试器窗口顶部的滑块让你可以快速拖动浏览各条绘制调用，以便迅速定位到感兴趣的条目。

Unity 向图形 API 发出绘制调用，以便在屏幕上绘制几何体。一条绘制调用告诉图形 API 要画什么以及怎么画。每条绘制调用都包含图形 API 所需的全部信息，例如有关纹理、着色器和缓冲区的信息。通常，为一条绘制调用所做的准备工作比绘制调用本身更耗费资源。

这一准备过程被归类到所谓的“渲染状态”（render state）之下。优化这一部分性能的一种方法是减少对渲染状态的更改次数。

帧调试器有助于定位绘制调用究竟来自何处。用它来可视化和理解渲染过程，从而指导你做出如何对绘制调用进行分组的决策，以减少对渲染状态的更改。

参照帧调试器的列表层级结构，可以定位那些值得关注的绘制调用来自何处。从列表中选择某一项后，Game 窗口中会显示场景渲染到该绘制调用为止（含该调用）的画面。

列表层级结构右侧的面板提供每条绘制调用的信息，例如几何体细节以及渲染所用的着色器。

其他有用的信息还包括：某条绘制调用为何无法与前一条合批（batching），以及对传入着色器的具体属性值的检查。

除了着色器属性值之外，ShaderProperties 区域还会显示这些属性被用于哪些着色器阶段（shader stages），例如 vertex、fragment、geometry、hull、domain。
