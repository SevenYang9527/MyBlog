工具与规范：把“感觉”变成可复查的数字

讲义第 31、32 页只放了两个标题：Profiler 和 FrameDebug。第 33、34 页讲美术制作规范。前者是“怎么定位”，后者是“怎么少挖坑”。两部分都不是引擎原理，但决定了优化能不能落地。

Profiler：先分清 CPU 和 GPU

UGUI 的开销可能出现在 CPU，也可能出现在 GPU。Profiler 里最值得先看的标记：

标记 / 模块说明看到它高时先想什么
Canvas.SendWillRenderCanvasesC# 侧 Rebuild 的总入口是不是每帧都在改 UI？Layout/Graphic 哪一段高？
CanvasUpdate.Layout布局三阶段布局组嵌套、ContentSizeFitter、文本变化导致的布局重算。
CanvasUpdate.PreRender / LatePreRenderGraphic 重建顶点生成、材质更新、Text/Tiled/Effect。
Canvas.BuildBatch原生批次构建元素太多、重叠太多、Canvas 太大、dirty 太频繁。
Graphic.OnPopulateMesh单个 Graphic 生成顶点长文本、Tiled Image、复杂自定义 Graphic。
Text.OnPopulateMeshLegacy Text 排版/生成长文本、Best Fit、频繁改字符串。
Font.RequestCharactersInTexture动态字体图集请求新字符太多、图集频繁重建。
EventSystem.Update / GraphicRaycaster.Raycast输入与点击检测Raycast Target 太多、全屏透明 Image、深层级。
WaitingForJob / PutGeometryJobFence等待 UI 几何 Job批次/顶点生成太重，主线程在等。

注意：UI / UI Details Profiler 模块收集的是 Editor-only 数据，官方文档明确说它在 development builds 里不工作。也就是说，你可以在 Editor 里用它看批次和断批原因，但最终的帧率/GPU 数据要在真机 development build 上用 Profiler、Frame Debugger 或平台工具看。

UI / UI Details 模块看什么

  • Self Batch Count：这个 Canvas 自己产生了多少批次。
  • Cumulative Batch Count：包含嵌套 Canvas 的累计批次。
  • Self / Cumulative Vertex Count：这个 Canvas 及其子 Canvas 的顶点数。
  • Batch Breaking Reason：为什么断批，常见有 Not Coplanar、CanvasInjectionIndex、Different Material/Texture/Rect Clipping/A8TextureUsage。
  • GameObject Count / GameObjects：每个批次包含哪些对象。

这张表比“猜”有用得多。先看哪个 Canvas 的批次/顶点异常，再看断批原因，最后回到 Hierarchy 调整。

Frame Debugger：看每一笔 DrawCall

Frame Debugger 能暂停一帧，按事件顺序展开绘制。对 UGUI 来说，重点看：

  • UI 的绘制事件有多少个，每个事件包含哪些对象。
  • 材质、纹理、Stencil、裁剪状态是否频繁切换。
  • 某个批次是不是被一个不同图集/不同材质的元素切断。
  • Overdraw：结合 Scene 视图的 Overdraw 模式或 RenderDoc，看像素被画了几次。

一个常见的误判是“DrawCall 少就一定快”。如果 DrawCall 少但都是全屏半透明，GPU 填充率仍然会爆。反过来，DrawCall 多但都是小图，CPU 可能先扛不住。Frame Debugger 和 GPU Profiler 要一起看。

美术规范：不是审美问题，是合批和内存问题

讲义第 33、34 页的规范建议，表面上是“团队协作”，实际上每一条都对应一个技术成本：

规范技术理由今天怎么做
设计模板（尺寸/布局/样式）减少重复结构、减少临时布局、统一合批顺序保留；用设计系统/ScriptableObject 管理尺寸和颜色。
路径一致性换图、打包、定位资源时不出错保留；配合 Addressables / Sprite Atlas 的命名规则。
图片命名可读性和自动化打包保留；用“功能_类型_颜色_尺寸”这类稳定规则，避免空格/中文路径。
公用图集减少重复纹理、方便合批按界面/功能拆 Sprite Atlas；公共图复制到独立图集会减少断批但增加内存，要实测。
合理出图尺寸减少包体、导入时间、显存按目标分辨率出图；UI 纹理通常关 Mipmap，使用 ASTC/ETC2 压缩。
图片分类不同类型的图有不同的打包策略UISprite（九宫格/平铺）、UIFrame（大背景）、Icon、Photo、原画分开管理。
字体大小分级控制字号数量，减少字体图集压力用 TMP Font Asset + 少量字号/材质；避免每个界面一套字号。
色值表减少“魔法颜色”，方便换肤用设计 token / ScriptableObject / USS 变量统一管理。

讲义里“大概百分之九十的窗口都在这几个模板中选择”是一个项目经验，不是行业统计。它想表达的是“模板化能显著降低 UI 生产成本”，这个方向值得保留；具体比例不用当真。

Sprite 与 Sprite Atlas 的现代检查清单

讲义没有展开图集设置，但这是 UI 性能里最容易出错的地方。下面这些设置有的在 Sprite Atlas 上，有的在纹理/Sprite 导入设置里；按项目逐项检查，不要混在一个面板里找。

  • Include in Build：该图集是否需要打进包；不要把所有图集都设成 include。
  • Allow Rotation / Tight Packing：能提高 packing 率，但可能影响图集内 Sprite 的朝向/网格；UI 九宫格图要谨慎。
  • Padding：防止相邻 Sprite 采样串色；压缩格式和 Filter 会影响所需 padding。
  • Max Texture Size：图集太大会增加显存和采样成本；按目标平台设置。
  • Compression：移动端优先 ASTC/ETC2；UI 文字/细线要测试压缩伪影。
  • Generate Mip Maps：UI 通常关闭；World Space UI 远距离可能需要，但要权衡。
  • Wrap Mode：普通 UI 用 Clamp；Tiled Image 想用纹理平铺时用 Repeat。
  • Filter Mode：像素风用 Point，普通 UI 用 Bilinear；和压缩/缩放一起测试。
  • Read/Write Enabled：不需要像素级 Raycast 时关闭，省一份内存。
  • Mesh Type：需要 Tight 多边形时设为 Tight，否则 Full Rect 更省顶点。

QA 检查清单

上线前，至少用目标最低配设备跑一遍：

  • UI 的 DrawCall / Batch 数量是否在预算内；有没有异常大的 Canvas。
  • 全屏 UI 的 Overdraw 是否过高；有没有被完全遮住却仍在绘制的面板。
  • 长文本、滚动列表、动态数字的 CPU 峰值是否可接受。
  • 字体图集是否频繁重建；生僻字/多语言是否缺字。
  • 所有装饰性 Graphic 的 Raycast Target 是否关闭；有没有全屏透明 Image 拦截点击。
  • Canvas 的 Pixel Perfect、Animator、LayoutGroup、ContentSizeFitter 是否在不需要时仍然开启。
  • UI 贴图/图集的实际内存和压缩格式是否符合目标平台。

考据结论：讲义第 31-34 页的工具体系和美术规范方向正确，但第 31-32 页只有标题，没有可核对的内容；第 33-34 页属于经验规范，不是绝对真理。今天需要补上 UI / UI Details Profiler、Frame Debugger、Sprite Atlas 设置、TMP 和真机验证。

把规范写成可执行的检查

规范如果只写在文档里，很容易变成“大家都知道，但没人检查”。更有效的做法是把关键项做成 Editor 检查或 CI 检查：

  • 扫描 UI Prefab，找出 raycastTarget = true 但没有交互组件的 Graphic。
  • 扫描 Image.sprite == null 的节点。
  • 扫描 Canvas 下的元素数量、嵌套 Canvas 数量、Mask 数量。
  • 扫描同时挂 Shadow 和 Outline 的长文本。
  • 扫描使用 Best Fit 的 Text，标记出来让负责人确认。
  • 在构建后输出各 Sprite Atlas 的大小和压缩格式。

这些检查不需要运行时开销，却能在提交前拦住大部分“明明知道但总会犯”的问题。
