DrawCall：合批优化不是“把东西塞进一个图集”

讲义第 27 页讲合批优化，给了五条：相同层级原则、Mask 组件、隐藏的 Image、Screen Space - Camera 模式、Hierarchy 穿插重叠。这五条都是实战里最常见的断批原因。本章把它们展开，并补上“为什么”和“怎么验证”。

先分清 Batch、SubMesh 和 DrawCall

三个词经常被混用：

  • Batch：UGUI 在一次合批中合并出来的一组可一起绘制的元素。
  • SubMesh：组合网格里按材质/纹理分出来的一段；通常一个 SubMesh 对应一个 DrawCall。
  • DrawCall：GPU 实际收到的一次绘制命令。

一个 Canvas 生成一个组合 Mesh，里面可以有多个 SubMesh；一个 Batch 也可能包含多个 DrawCall（例如一个材质下有多个 SubMesh）。所以“批次少”通常意味着“DrawCall 少”，但两者不是一一对应。优化时以 Frame Debugger 的 DrawCall 数和 UI Profiler 的 Batch Count 为准。

原则一：相同层级 / 相邻顺序

讲义说“父节点下所有子节点，尽量保持相同的层次结构，相同层级下的 UI 元素可以 Batch”。更准确地说：把使用同一图集/材质、会一起出现、不会互相穿插的元素放在相邻的 Hierarchy 位置。这样它们在深度排序后更容易相邻，从而被贪心合并。

“相同层级”不是充分条件。两个元素即使在同一层，如果中间夹了一个不同图集的元素，或者它们不共面，仍然不能合批。反过来，不同父节点下的元素只要在最终绘制顺序里相邻且满足条件，也可以合批。

原则二：Mask 与 RectMask2D

讲义的“Mask 组件使用了模板缓存，Mask 中的 UI 元素无法与外界 UI 元素合批，Mask 组件还会额外增加 2 个 DrawCall”基本成立，但要把两个组件分开：

组件原理DrawCall 成本适用
Mask模板缓冲（Stencil）：先写入模板，再让子元素按模板测试绘制，最后清除。常见经验是额外 2 个（写入 + 清除），嵌套/内容更多时可能更多；会打断内外合批。圆形头像、异形裁剪、需要任意形状遮罩。
RectMask2D矩形裁剪，不需要 Stencil；直接设置裁剪矩形并剔除窗口外元素。通常不增加额外 DrawCall，但会改变裁剪状态、打断批次；比 Mask 省。ScrollView、矩形窗口、列表裁剪。

所以“Mask 一定加 2 个 DrawCall”是一个经验值，不是引擎保证；但“Mask 会打断合批、比 RectMask2D 贵”是可靠的方向。能用 RectMask2D 就别用 Mask；必须用 Mask 时，减少嵌套层数，尽量不要把 Mask 放在大量元素的中间。

原则三：隐藏的 Image

讲义说“Image 组件中 sprite 为空，都是占用 drawcall 渲染的，并且还会打断前后元素的合批”。这句话容易被误解成“sprite 为空就不画”。实际相反：Image 在 activeSprite == null 时会走基类 Graphic.OnPopulateMesh，生成一个使用白色纹理的 quad。它会占绘制、用白图纹理，并且因为纹理不同而打断合批。

常见来源：

  • 为了点击热区放了一个空 Image。
  • 美术把 Image 的 Sprite 清空了，但组件还在。
  • 用 Image 做占位，运行时再换图；在换图前它一直在画白块。

处理：删掉空 Image；需要热区就写一个 OnPopulateMesh 为空的 Graphic；需要占位就禁用 CanvasRenderer 或整个对象，等有图再启用。

原则四：Screen Space - Camera 与屏幕外元素

讲义说“一个 Canvas 中的任何一个 UI 元素只要在屏幕中，则这个 Canvas 中的其他 UI 元素即使在屏幕外 DrawCall 仍不会减少”。这句话描述的是 Canvas 级的渲染单元特性：一个 Canvas 通常作为一个整体提交，Unity 不会因为某个 Graphic 在屏幕外就把它单独剔除出批次。屏幕外元素仍然可能参与合批、占用顶点和 DrawCall。

所以不要指望“把元素挪到屏幕外”来省 DrawCall。有效的做法是：

  • 把屏幕外/低频率的内容拆到独立 Canvas，按需禁用 Canvas 组件。
  • 用 RectMask2D 裁剪窗口外元素；它会剔除完全在裁剪矩形外的可绘制元素。
  • 滚动列表用池化，而不是把几百个元素都放在 Content 里。
  • 用 Frame Debugger 确认“屏幕外元素”到底还在不在批次里。

原则五：Hierarchy 穿插重叠

讲义的红点/Icon 例子很典型：红点和 Icon 来自不同图集；红点稍微大一点，遮住了旁边的 Icon，就不能合批。原因不是“红点太大”，而是“红点夹在了本来可以合批的 Icon 之间，破坏了绘制顺序”。

调整节点关系时不能只看“合批”，还要保证视觉上层级正确。把红点全部放到 Icon 上面可能会改变遮挡关系；如果红点本来就应该盖住 Icon，那就要接受这种断批，或者把 Icon 和红点做进同一张图集/同一个材质。

还有哪些常见断批源

断批源为什么怎么改
不同 Sprite Atlas纹理不同，无法共用材质按界面/功能打图集；避免在中间穿插另一图集。
不同 Material Preset（TMP）材质实例不同统一 Font Asset 和 Material Preset；少用逐字不同的材质。
Z 偏移 / 旋转不共面（Not Coplanar With Canvas）可合批元素保持 Z=0、无旋转；旋转元素单独分组。
CanvasGroupCanvasInjectionIndex 强制新批次淡入淡出挂在面板根，不要每个元素挂一个。
MaskStencil 状态变化矩形裁剪用 RectMask2D；减少嵌套 Mask。
空 Image白色纹理 quad删除或用不绘制的 Raycast Graphic。
自定义 Shader / 多材质材质实例或关键字不同共享材质；用顶点数据/材质属性而不是多份材质。

考据结论：讲义第 27 页的五条方向都成立，但要注意：相同层级只是启发式；Mask 的“2 个 DrawCall”是经验值；空 Image 确实会画白 quad 并断批；Screen Space - Camera 的屏幕外元素不会自动省 DrawCall；Z 偏移主要影响共面/合批，渲染顺序主要由层级和排序决定。

用工具验证，而不是背数字

同一个界面在不同 Unity 版本、不同图集设置、不同平台上，批次数可能不同。最可靠的验证组合是：

  • Frame Debugger：看每个 UI 绘制事件包含哪些对象，Stencil、材质、纹理是什么。
  • UI / UI Details Profiler：看每个 Canvas 的 Self/Cumulative Batch Count、Vertex Count、Batch Breaking Reason。
  • Profiler Timeline：看 Canvas.BuildBatch 和 Canvas.SendWillRenderCanvases 的耗时，确认优化的是 CPU 还是 GPU。

如果 Frame Debugger 里看到很多“UI/Default”事件，每个事件只包含一两个对象，通常说明批次被切得很碎；如果看到少数几个事件包含大量对象，说明合批不错，接下来该看 Overdraw 和顶点数。
