Rebuild 不是一个动作，而是三层管线

讲义第 19 到 22 页开始进入 UGUI 的内部：Canvas Batch、网格重建因素、Rebuild 流程图，以及“为什么 rebuild layout 时要优先处理根节点”。这部分信息密度很高，但也最容易把三件不同的事混成一件：

  • Layout Rebuild：布局组件重新计算尺寸和位置。
  • Graphic Rebuild：Graphic 重新生成顶点和材质。
  • Canvas Batch Rebuild：原生 Canvas 重新排序、合批、生成组合网格。

日常说“这个 UI 触发了 Rebuild”，可能指其中任意一层。优化时如果不区分，就会得出“少改颜色就能减少 DrawCall”这种似是而非的结论。

谁会弄脏 UI

改动触发什么说明
改 Graphic.colorGraphic Rebuild（顶点色）颜色写在 UIVertex.color 里，不会换材质，但仍要重建网格；也会让 Canvas 批次变脏。
改 Text.textGraphic + Layout Rebuild文字变了，顶点要重排；如果文本参与布局，还要重算尺寸。
改 RectTransform 的尺寸 / 锚点 / 轴心通常触发 Graphic + Layout尺寸变化会触发 OnRectTransformDimensionsChange，进而 SetVerticesDirty 和 SetLayoutDirty。
只改 RectTransform 的位置Canvas Batch Rebuild本地顶点没变，但变换矩阵变了，Canvas 需要重新合批；Pixel Perfect 开启时还可能强制重建顶点。
启用 / 禁用 GameObject 或组件OnEnable 触发 SetAllDirty重新启用通常意味着 Layout + 顶点 + 材质全部重来；整块面板隐藏时，禁用 Canvas 组件更省。
Animator 写入 UGUI 属性OnDidApplyAnimationProperties → SetAllDirty被动画驱动的属性每帧写入时都可能弄脏；不一定每次都有视觉变化。
换 Sprite / 换材质SetAllDirty / SetMaterialDirty图集或材质变化会改变合批条件，通常也会打断批次。

讲义第 20 页说“修改 Image、Text 的 color 会改变 UIVertex.color；修改 RectTransform 的 Size、Anchors、Pivot 会改变 UIVertex.position”。前半句对；后半句要分情况：尺寸变化确实会改变顶点位置，纯位置变化不会改本地顶点，Anchors/Pivot 只有在改变矩形尺寸或局部矩形原点时才需要重建顶点。把所有 RectTransform 改动都当成“顶点重建”会高估成本，也会找错瓶颈。

CanvasUpdateRegistry 的流水线

UGUI 的 C# 侧 Rebuild 由 CanvasUpdateRegistry 调度。它监听 Canvas.willRenderCanvases，每帧在渲染前执行一次 PerformUpdate。顺序大致是：

  1. 清理已经销毁的注册项。
  2. 把 Layout 重建队列按“父节点数量”排序，越靠近根越先处理。
  3. 依次执行 Prelayout、Layout、PostLayout 三个阶段。
  4. 执行裁剪（ClipperRegistry.Cull），让 Mask / RectMask2D 剔除不可见元素。
  5. 依次执行 PreRender、LatePreRender 两个 Graphic 重建阶段。
  6. 标记完成，清空队列。

为什么“根节点优先”和“自底向上”不矛盾

讲义问：“为什么在 rebuild layout 的时候，要优先处理根节点的元素？”答案要分两个方向看：

  • 布局计算（CalculateLayoutInput）是自底向上：父布局组要知道子元素的 preferred size，才能算出自己的尺寸。所以 LayoutRebuilder 在计算阶段先递归子节点，再处理父节点。
  • 布局控制（SetLayout）是自顶向下：父布局组决定子元素能占多大空间，再把子元素摆进去。所以控制阶段必须先父后子。

CanvasUpdateRegistry 的队列按父节点数量升序排序，保证父级布局控制器先于子级执行；而 LayoutRebuilder.Rebuild 内部先做 CalculateLayoutInputHorizontal（递归子节点）再做 SetLayoutHorizontal（父先子后），然后同样的顺序做垂直方向。这样既满足“子元素先报尺寸”，又满足“父元素先分配空间”。

考据结论：讲义说“Layout 队列按 hierarchy 排序、越靠近根越优先”是对的，但只说了控制阶段；“布局计算自底向上、布局控制自顶向下”才是完整答案。把 Rebuild 笼统说成一个过程也不够，至少要区分 Layout、Graphic、Batch 三层。

Canvas 批次重建：真正的“全量分析”

讲义引用了 Unity 官方的重要提示：当 Canvas 上任何可绘制元素发生变化时，Canvas 必须重新执行合批过程，并重新分析 Canvas 上的每个可绘制元素，不管它是否被修改。这个说法是准确的，也是“动静分离”最重要的理由。

但要注意，“重新分析每个元素”不等于“重新生成每个元素的顶点”。顶点有 CanvasRenderer 级缓存：只要 UpdateGeometry 没被调用，就可以复用；真正全量的是 Canvas 级的排序和合批。所以一个元素移动时，可能只触发批次重建，而不触发所有元素的顶点重建；但批次重建本身仍然与 Canvas 上的元素数量相关。

子 Canvas 的价值就在这里：子 Canvas 有自己的批次，子 Canvas 内的 dirty 不会让父 Canvas 重新合批。反过来，父 Canvas 的改动也不一定会让子 Canvas 重算。把更新频率不同的 UI 分到不同 Canvas，可以把“全量分析”的范围缩小。

什么时候该强制刷新

有些场景需要立刻拿到布局结果，例如打开面板后马上根据内容高度定位、或者在做截图/导出。UGUI 提供了两个强制入口：

// 立刻重建某个布局根（谨慎使用）
LayoutRebuilder.ForceRebuildLayoutImmediate(rootRectTransform);

// 立刻让所有 Canvas 执行一次更新（更重，不要每帧调用）
Canvas.ForceUpdateCanvases();

这两个 API 都会把原本可以合并到帧末的工作提前执行，打乱批处理节奏。正确用法是“在必要的时间点调用一次”，而不是“在 Update 里每帧调用”。如果发现自己需要频繁强制刷新，通常说明布局结构或数据更新方式需要改。

用 Profiler 区分三层开销

在 Profiler 里，常见的相关标记包括：

  • Canvas.SendWillRenderCanvases：C# 侧 Rebuild 的总入口。
  • CanvasUpdate.Prelayout / Layout / PostLayout：布局三阶段。
  • CanvasUpdate.PreRender / LatePreRender：Graphic 重建。
  • Canvas.BuildBatch：原生批次构建。
  • Graphic.OnPopulateMesh / Graphic.ModifyMesh：具体 Graphic 的顶点生成和修改。
  • WaitingForJob / PutGeometryJobFence：等待 UI 几何 Job 的同步点。

看到 Canvas.BuildBatch 高，优先考虑拆 Canvas、减少元素、减少重叠；看到 Graphic.OnPopulateMesh 高，优先考虑文本、Tiled Image、复杂的自定义 Graphic；看到 CanvasUpdate.Layout 高，优先考虑布局组嵌套、ContentSizeFitter、频繁改文本导致的布局重算。

本章要点：Rebuild 分三层；Layout 计算自底向上、控制自顶向下；Canvas 批次是全量分析但顶点有缓存；子 Canvas 能隔离批次；强制刷新是工具，不是常规操作。
