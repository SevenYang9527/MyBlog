03 · Canvas：渲染模式、层级顺序与“谁在谁上面”

Canvas 不是背景板，它是渲染单元

讲义第 5 页把 Canvas 比作“油画的画布”：所有 UI 元素都要作为它的子对象才能被渲染，画布控制 UI 的渲染。这个比喻很好，但不够用。更准确地说，Canvas 是 UGUI 的渲染与合批单元：它决定这些 UI 元素最终怎样被组织成网格、怎样排序、怎样提交给 GPU。

所有可见的 UGUI 元素都需要一个 Canvas 祖先。每个 Graphic（Image、Text、RawImage 等）身上会有一个 CanvasRenderer，它负责把 C# 生成的网格交给原生 Canvas。一个 Canvas 下的元素会被收集、排序、合批，生成一个组合网格；子 Canvas 则会单独成组，形成自己的批次。

绘制顺序：Hierarchy 从上到下，就是从前到后

讲义说“画布上的 UI 元素按照排列顺序渲染，位于上方的元素先被渲染，下方的元素后被渲染；嵌套结构先渲染父类，再渲染子类”。这句话大方向是对的，但“上方/下方”容易和屏幕空间混淆。更准确的表述是：

  • UGUI 按 Hierarchy 顺序 绘制，采用深度优先遍历。
  • 同一个父节点下，排在前面的子物体先画，也就是在更底层；排在后面的子物体后画，盖在更上面。
  • 如果父物体自己也有 Graphic，父物体的图形先于它的子物体绘制；然后按子物体顺序继续。
  • 屏幕上的“谁遮住谁”由这个顺序决定，而不是由 Transform 的 Z 值单独决定（World Space 和 Screen Space - Camera 下 Z 还会影响与相机的距离）。

因此，讲义里“上方的元素先渲染、下方的元素后渲染”要理解成“Hierarchy 里靠上的先画、靠后的后画”。在 Editor 里拖动排序，本质上就是在改这个顺序。脚本里可以用 Transform.SetAsFirstSibling、SetAsLastSibling、SetSiblingIndex 调整。

三种渲染模式

模式核心行为适用场景常见坑
Screen Space - Overlay不需要相机，UI 在场景渲染之后直接覆盖屏幕；分辨率变化时自动匹配屏幕。大多数 HUD、菜单、弹窗不受相机 Culling Mask / Layer 影响；多个 Overlay Canvas 靠 Sorting Order 排序；不能夹在 3D 物体之间。
Screen Space - CameraCanvas 放在指定相机前的一段距离，由该相机渲染；相机参数会影响 UI（透视、FOV 等）。需要后处理、需要和 3D 物体交错、需要相机裁切的 UI场景物体可能挡在 UI 前面；相机 Culling Mask 只看 Canvas 所在 Layer，子物体的 Layer 不一定生效；相机移动/旋转要同步。
World SpaceCanvas 是普通 3D 对象，可以移动、旋转、缩放；UI 元素按 3D 位置参与排序。世界内看板、VR/AR、角色头顶血条、场景内交互面板需要 Event Camera；像素密度受 Canvas Scaler 的 Dynamic Pixels Per Unit 影响；距离缩放和文字清晰度要单独调。

讲义说 Overlay “永远在屏幕的最上面”。这句话在“相对于场景物体”的语境下成立，但不要理解成“绝对在所有 Canvas 之上”：多个 Overlay Canvas 之间仍然按 Sorting Layer / Sorting Order 排序；嵌套 Canvas 还可以用 Override Sorting 改变顺序。

Canvas 与 CanvasRenderer 的分工

理解 UGUI 的性能，先把三个概念分开：

  • Canvas：合批和渲染的根。一个 Canvas 的元素会一起参与批次构建；子 Canvas 会隔离出来，单独构建。
  • CanvasRenderer：每个 Graphic 身上的渲染代理。它接收 C# 生成的网格、材质、纹理和透明度，供 Canvas 合批。
  • Graphic：C# 侧的可见元素基类，负责 OnPopulateMesh 生成顶点、UpdateMaterial 更新材质，以及把“脏了”注册到 Rebuild 队列。

所以“Canvas 下的所有 UI 元素最终都会被 Batch 到同一个 Mesh”这句话要加两个限定：一是“同一个 Canvas 下、没有被 Sub-canvas 隔离、没有被裁剪掉的可绘制元素”；二是“一个 Mesh 里可能有多个 SubMesh，也就是多个 DrawCall”。Canvas 的目标是尽量减少 DrawCall，不是“保证只有一个”。

Layer 能隐藏 UI 吗？

讲义在后面（第 26 页）提到“通过修改 Canvas 对象的 Layer 隐藏面板”。这个做法在 Screen Space - Overlay 下不成立：Overlay Canvas 不经过相机，所以相机的 Culling Mask 管不到它。Unity 官方文档也明确说，UI 元素和 screen space canvas 的子物体是 Culling Mask 的例外，会照常渲染。

在 Screen Space - Camera 下，相机确实会按 Canvas 所在 Layer 做裁剪，但通常看的是 Canvas 根对象的 Layer，而不是每个 UI 子物体的 Layer。想隐藏整块面板，最稳的做法是禁用 Canvas 组件或直接禁用 GameObject；具体取舍在第 10 章讲。

考据结论：讲义对 Canvas 渲染模式和绘制顺序的描述大体正确，但有三处要补：Overlay 的“最上面”只相对于场景；一个 Canvas 生成的是一个含多个 SubMesh 的 Mesh，不是天然一个 DrawCall；Layer 不是 Overlay UI 的隐藏开关。

一段可运行的检查代码

如果你不确定当前 UI 到底挂在哪个 Canvas、用什么模式，可以在运行时打印出来：

using UnityEngine;
using UnityEngine.UI;

public class CanvasProbe : MonoBehaviour
{
    void Start()
    {
        var canvas = GetComponentInParent<Canvas>();
        if (canvas == null)
        {
            Debug.Log("不在任何 Canvas 下");
            return;
        }

        Debug.Log($"renderMode = {canvas.renderMode}, " +
                  $"root = {canvas.rootCanvas.name}, " +
                  $"sortingLayer = {canvas.sortingLayerName}, " +
                  $"sortingOrder = {canvas.sortingOrder}, " +
                  $"overrideSorting = {canvas.overrideSorting}, " +
                  $"scaleFactor = {canvas.scaleFactor}");
    }
}

把这段挂在任意 UI 元素上，至少能避免“以为它在 Overlay，其实在 Camera 模式”的低级误判。
