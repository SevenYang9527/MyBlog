第 10 章 游戏大厅和房间

原书的大厅/房间模块包括列表、房间面板、协议设计（查询战绩、房间列表、创建房间、进入房间、房间信息、离开房间、开始战斗）、服务端玩家/房间数据、消息处理、房间状态。

房间是一个小型状态机：等待玩家 → 准备/选阵营 → 开始战斗 → 战斗结束 → 返回房间/解散。服务端要维护房主、玩家列表、阵营、准备状态、房间容量、超时/断线；客户端只发意图、展示状态。

这一章的核心是“多人状态的一致性”：谁在房间里、谁是房主、能不能开始、断线怎么办。

原书脉络

  • 10.1 列表面板；10.2 房间面板；10.3 协议设计（战绩/房间列表/创建/进入/信息/离开/开始）。
  • 10.4 列表面板逻辑；10.5 房间面板逻辑；10.6-10.12 服务端玩家/房间/消息处理。

关键实现：房间状态

房间是服务端维护的共享状态：房主、玩家列表、阵营、准备、容量、状态（Waiting/Playing）。客户端只发意图，服务端校验并广播新状态；列表用“版本号/增量”避免全量刷新。

public class Room
{
    public int Id;
    public int OwnerId;
    public RoomState State = RoomState.Waiting;
    public readonly Dictionary<int, PlayerData> Players = new();
    public int Capacity = 8;

    public bool CanStart()
        => State == RoomState.Waiting
        && Players.Count >= 2
        && Players.Values.All(p => p.Ready);
}

常见坑

  • 两个客户端同时加入最后一个位置，超员；服务端要原子校验。
  • 房主退出没有迁移/解散，房间卡死。
  • 列表数据过期；用版本号/推送/定时刷新。
  • 开始战斗时客户端状态不一致；以服务端快照为准。

练习

给房间加“准备/取消准备、换阵营、踢人、房主迁移”；用 Redis 存房间状态并测试服务重启恢复。

2026 更新：大规模房间可用 Redis 维护状态、分布式锁/幂等防重复加入；断线重连/房主迁移/匹配超时要做；PlayFab/Nakama/Photon 提供现成大厅/房间能力。

本章要点：大厅/房间 = 列表 + 房间状态机；协议查询/创建/进入/离开/开始；服务端维护房主/玩家/阵营/准备/容量；断线/超时/重连要设计。
