单例模式（Singleton Pattern）

单例（Singleton）的名声不太好。如果你刚开始做 Unity 开发，单例很可能是你在实际项目中最早能辨认出来的模式之一。它同时也是最受诟病的设计模式之一。

根据最初的“四人帮”（Gang of Four）的说法，单例模式：

  • 确保一个类只能实例化它自身的一个实例；
  • 提供对该单一实例的便捷全局访问。

如果你需要恰好有一个对象来协调整个场景中的各种操作，这会很有用。例如，你可能希望场景中恰好有一个游戏管理器（game manager）来指挥主游戏循环。你也可能希望同一时间只有一个文件管理器（file manager）在向文件系统写入数据。像这样处于中心位置、管理器层级的对象，往往就是单例模式的合适候选。

在《Game Programming Patterns》一书中，作者指出单例弊大于利，并将其列为反模式（anti-pattern）。这种糟糕的声誉源于该模式用起来太容易，因而容易被滥用。开发者往往在不恰当的场合套用单例，从而引入不必要的全局状态或依赖。

下面我们来考察如何在 Unity 中构建单例，并权衡它的优缺点。之后你就可以判断是否值得把它引入自己的应用。

示例：简单单例

最简单的单例之一可能长这样：

using UnityEngine;
public class SimpleSingleton : MonoBehaviour
{
    public static SimpleSingleton Instance;
    private void Awake()
    {
        if (Instance == null)
        {
            Instance = this; 
        }
            else
        {
            Destroy(gameObject); 
        }
    }
}

公共静态字段 Instance 将持有场景中这个 Singleton 的唯一实例。在 Awake 方法中，检查它是否已经被赋值。如果 Instance 当前为 null，就把 Instance 设为这个特定的对象——它必须是场景中的第一个单例。否则，这个实例必定是重复的；你调用 Destroy(gameObject) 来保证你的单例在场景中只有一个这样的组件。

如果在运行时把这个脚本挂到层级视图（Hierarchy）中的多个 GameObject 上，Awake 中的逻辑会保留第一个对象，然后丢弃其余的。

Instance 字段是 public 且 static 的。任何组件都可以从场景中的任意位置全局访问这个唯一的单例。

持久化与延迟实例化

SimpleSingleton 按目前写法可以正常工作。不过，它确实存在两个问题：

  • 加载新场景会销毁该 GameObject。
  • 你需要在层级视图中预先设置好单例，然后才能使用它。

由于单例常常充当无处不在的管理器脚本，把它做成持久化的对象（使用 DontDestroyOnLoad）会带来好处。

此外，你还可以使用延迟实例化（lazy instantiation），在第一次需要它时才自动构建这个单例。你只需要一些逻辑来创建一个 GameObject，然后添加相应的 Singleton 组件。

改进后的单例大致如下：

  public class Singleton : MonoBehaviour
  {
        private static Singleton instance;
        public static Singleton Instance
        {
            get
            {
                if (instance == null)
                {
                    SetupInstance();
                }
                return instance;
            }
        }
        private void Awake()
        {
            if (instance == null)
            {
                instance = this;
                DontDestroyOnLoad(this.gameObject);
            }
            else
            {
                Destroy(gameObject);
            }
        }
        private static void SetupInstance()
        {
            instance = FindObjectOfType<Singleton>();
            if (instance == null)
            {
                GameObject gameObj = new GameObject();
                gameObj.name = "Singleton";
                instance = gameObj.AddComponent<Singleton>();
                DontDestroyOnLoad(gameObj);
            }
        }

现在 Instance 是一个公共属性，指向私有的 instance 后备字段。第一次引用这个单例时，会在 getter 中检查 Instance 是否存在。如果它不存在，SetupInstance 方法就会创建一个带有相应组件的 GameObject。

DontDestroyOnLoad(gameObject) 可以防止场景加载时把单例从层级视图中清除。单例实例现在是持久化的，即使你在游戏中切换场景，它也会保持活动状态。

使用泛型

这两个版本的脚本都没有解决如何在同一个场景中创建不同单例的问题。例如，如果你想要一个充当 AudioManager 的单例，以及另一个充当 GameManager 的单例，它们目前无法共存。你只能复制相关代码，把其中的逻辑粘贴到每个类里。

换个做法，把脚本改成泛型版本，如下所示：

public class Singleton<T> : MonoBehaviour where T : Component
{
    private static T instance;
    public static T Instance
    {
        get
        {
            if (instance == null)
            {
                instance = (T)FindObjectOfType(typeof(T));
                if (instance == null)
                {
                    SetupInstance();
                }
            }
            return instance;
        }
    }
    public virtual void Awake()
    {
        RemoveDuplicates();
    }
    private static void SetupInstance()
    {
        instance = (T)FindObjectOfType(typeof(T));
        if (instance == null)
        {
           GameObject gameObj = new GameObject();
           gameObj.name = typeof(T).Name;
           instance = gameObj.AddComponent<T>();
           DontDestroyOnLoad(gameObj);
        }
    }
    private void RemoveDuplicates()
    {
        if (instance == null)
        {
            instance = this as T;
            DontDestroyOnLoad(gameObject);
        }
        else
        {
            Destroy(gameObject);
        }
    }
}

这样一来，你可以把任何类变成单例。声明类时，只需继承这个泛型单例即可。例如，你可以像下面这样声明，把一个名为 GameManager 的 MonoBehaviour 变成单例：

public class GameManager: Singleton<GameManager>
{
    // ...
}

之后，无论何时需要，你都可以直接引用公共静态的 GameManager.Instance。

优点与缺点

单例与本书中的其他模式不同，它在多个方面违背了 SOLID 原则。许多开发者出于各种原因不喜欢它：

  • 单例需要全局访问：由于你把它们当作全局实例来使用，它们会隐藏许多依赖关系，使 bug 更难排查。
  • 单例让测试变得困难：单元测试必须彼此独立。由于单例可能改变场景中许多 GameObject 的状态，它们会干扰你的测试。
  • 单例助长紧耦合：本书中的大多数模式都试图解耦依赖关系。单例恰恰相反。紧耦合会让重构变得困难。如果你改动了一个组件，就可能影响到与它相连的任何组件，从而导致代码不整洁。

反对单例的理由相当充分。如果你正在构建一款企业级游戏，并预期未来多年都要维护它，那你也许应该避开单例。

但许多游戏并不是企业级应用。你不需要像对待商业软件那样持续地扩展它们。

事实上，如果你正在做一款不需要扩展性的小游戏，单例提供的一些好处可能对你很有吸引力：

  • 单例学起来相对快：核心模式本身比较直白。
  • 单例对使用者友好：要在另一个组件中使用你的单例，只需引用那个公共且静态的实例。单例实例随时可以从场景中的任何对象按需获取。
  • 单例性能好：由于你始终可以全局访问静态的单例实例，就能避免缓存 GetComponent 或 Find 操作的结果，而这些操作往往很慢。

通过这种方式，你可以做一个管理器对象（例如游戏流程管理器或音频管理器），让它始终可以从场景中的其他任何 GameObject 访问。另外，如果你已经实现了对象池（Object Pool），也可以把池化系统设计成单例，让获取池化对象更容易。

如果你决定在项目中使用单例，请把它们保持在最低数量。不要不加区分地使用。把单例留给少数确实能从全局访问中受益的脚本。
