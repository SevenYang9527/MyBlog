第 01 章 · 坐标系统

一个顶点，要走五段路才上屏幕

原教程用了整整一章、几百行代码来讲空间变换。但在 Unity 里，你几乎只会碰到其中一段：Local → World，也就是 Transform。剩下的 Camera 和投影，Unity 已经算好了。这一章只讲你真正需要的那部分，以及「什么时候会算错」。

一句话

顶点从「模型自己」出发，被一组矩阵一路搬到屏幕上。Unity 替你算完了后面三段，但它不会替你判断你此刻在哪个空间里做运算——而 90% 的 Shader bug 就是空间搞错了。

为什么需要这么多空间

想象一把椅子。它有三个完全不同的「位置」：

  • 在建模软件里，它站在自己文件的原点旁边 —— 这是局部空间（Local）
  • 在场景里，你把它拖到 (5, 0, 3) —— 这是世界空间（World）
  • 在玩家眼睛里，它可能偏左 30 厘米 —— 这是观察空间（View）
  • 在屏幕上，它占据第 640 到 800 个像素 —— 这是屏幕空间（Screen）

这几个「位置」都是对的，只是参考系不同。坐标系统这一章，本质上就是在讲「怎么在参考系之间换算」，以及「GPU 只认识哪一种」。

GPU 最后只认识屏幕上的像素，所以每个顶点都得被搬运过去。搬运的过程是固定的五步，这也是图形管线最核心的一条主线：

六个空间，一张表看清

不要被「六个」吓到。你真正要记住的只有两件事：每个空间的原点在哪，以及Unity 里用哪个 API 拿到它。

三个矩阵，各干一件事

M：模型矩阵 —— 把物体摆进世界

模型矩阵就是把 Position、Rotation、Scale 打包成一个 4×4 矩阵。Unity 里你改 Transform 面板，改的就是这个矩阵的参数。

注意它同时包含缩放。这带来一个隐患：如果缩放是非均匀的（比如 X 拉两倍、Y 不变），法线就不能直接用这个矩阵变换了——必须用它的逆转置。Unity 帮你处理了这件事，提供 UnityObjectToWorldNormal()；但如果你自己手搓，很容易踩到。

V：视图矩阵 —— 把世界搬到相机面前

关键认知：相机不动，是整个世界在动。视图矩阵是相机变换的「逆」：相机往前 1 米，等价于世界整体往后 1 米。下一章会用一整节讲这件事。

Unity 的观察空间是右手系

Unity 的世界空间是左手系（Z 向前），但 worldToCameraMatrix 会把 Z 轴翻转一次，让观察空间变成右手系、相机朝 −Z，以兼容 OpenGL 的老习惯。所以：世界空间里相机前方是 +Z，观察空间里同一个方向变成 −Z。算「物体在相机前面还是后面」时，这一步特别容易搞反。

P：投影矩阵 —— 把视锥体压成一个方块

投影矩阵做了两件看起来毫不相干的事：

  1. 形状：把「远处大、近处小」的视锥体，压成一个标准的立方体（−1..1），这样 GPU 才能做裁剪和光栅化。
  2. 深度：把「距离」编码进 z 分量，顺便写进 w。这就是为什么后面的「透视除法」能产生近大远小的效果——离得越远，w 越大，除完之后坐标越靠近中心。

它不是均匀压缩：近处的深度占了很多精度，远处很少。这也是「近裁剪面设得太小会导致 z-fighting」的原因。

乘法顺序：为什么是 P × V × M

图形学里的向量是列向量，矩阵在左边相乘：结果 = P × V × M × 顶点。因为是从右往左依次作用，所以写代码时顺序不能反——写成 M × V × P 得到的是垃圾数据，画面直接空白或镜像。

C# 手动走一遍 MVP，验证 Unity 背后做了什么 
using UnityEngine;

public class ManualMVP : MonoBehaviour
{
    public Camera cam;

    void Start()
    {
        // 1. 三个矩阵
        Matrix4x4 M = transform.localToWorldMatrix;                            // 局部 → 世界
        Matrix4x4 V = cam.worldToCameraMatrix;                                 // 世界 → 观察
        Matrix4x4 P = GL.GetGPUProjectionMatrix(cam.projectionMatrix, false);  // 观察 → 裁剪

        // 2. 列向量左乘，从右往左依次作用，所以必须写成 P * V * M
        Matrix4x4 MVP = P * V * M;

        // 3. 用模型原点试一下（齐次坐标，w = 1）
        Vector4 local = new Vector4(0f, 0f, 0f, 1f);
        Vector4 clip  = MVP * local;          // 得到裁剪空间坐标，w 里存着深度信息

        // 4. 透视除法：GPU 在裁剪之后自动做这一步
        Vector3 ndc = new Vector3(clip.x / clip.w, clip.y / clip.w, clip.z / clip.w);

        // 5. NDC（-1..1）→ 像素（0..宽）
        Vector3 pixel = new Vector3((ndc.x * 0.5f + 0.5f) * Screen.width,
                                    (ndc.y * 0.5f + 0.5f) * Screen.height,
                                    0f);

        // 6. 和 Unity 自己算的结果对比，应该几乎一致
        Debug.Log($"手算 {pixel} / Unity {cam.WorldToScreenPoint(transform.position)}");
    }
}

把这段挂到任意物体上、拖一个相机进去、点 Play，看 Console 里两个值是否对得上。这是建立空间感最有效的一次练习——比读十遍「MVP 变换」都有用。

Unity 里，你其实只关心其中一段

因为剩下四段 Unity 都封装好了。你在 Shader 里最常见的写法是：

HLSL · 内置管线 最小顶点/片元着色器：空间变换只有一行 
Shader "Custom/SpaceDemo"
{
    SubShader
    {
        Pass
        {
            CGPROGRAM
            #pragma vertex vert
            #pragma fragment frag
            #include "UnityCG.cginc"

            struct appdata { float4 vertex : POSITION; float3 normal : NORMAL; };
            struct v2f { float4 pos : SV_POSITION; };

            v2f vert (appdata v)
            {
                v2f o;
                // 这一行 = P * V * M * 顶点，内部自动处理了平台差异
                o.pos = UnityObjectToClipPos(v.vertex);
                return o;
            }

            fixed4 frag (v2f i) : SV_Target
            {
                return fixed4(1, 1, 1, 1);   // 纯白
            }
            ENDCG
        }
    }
}

UnityObjectToClipPos 这七个字母，就是原教程里那一大段矩阵乘法的全部。想拿中间结果，Unity 还提供了这些：

局部 → 世界mul(unity_ObjectToWorld, pos)TransformObjectToWorld(pos)

Shader Graph 里的「空间」下拉框

Shader Graph 的 Position 节点上有一个 Space 下拉框：Object、World、View、Clip、Screen。这五个选项和本章的五个空间一一对应。当你发现「把 Position 节点从 Object 切到 World，效果就对了」，那不是玄学，就是这一章讲的东西。

顺带一个必须知道的东西：深度

投影矩阵把深度压进了 z（并且写进 w），而 GPU 靠这个值判断「谁在前面」。这里有两个反直觉的事实：

  1. 深度不是线性的。经过透视除法之后，靠近近裁剪面的深度变化非常剧烈，远处的挤压在一起。所以「近裁剪面越小，远处越没有精度」。
  2. 深度值范围因平台而异。OpenGL 是 −1..1，Direct3D / Metal / Vulkan 是 0..1，而且 y 轴方向还可能翻转。这就是 GL.GetGPUProjectionMatrix() 存在的原因——它会把 Unity 的「通用投影矩阵」翻译成当前图形 API 真正想要的格式。

两个经典翻车现场

  • z-fighting：把近裁剪面设成 0.01，于是 10 米外的墙开始闪烁。改成 0.1 或 0.3，问题消失。远处的东西不需要那么高的深度精度。
  • 自己拼投影矩阵：直接 camera.projectionMatrix 传给 Shader，在 Windows 上正常、打包到 Android 就上下颠倒或深度全黑。正确做法是用 GL.GetGPUProjectionMatrix(proj, 是否渲染到纹理)。第 05 章讲帧缓冲时，这个参数会再次出现。

五个坑

症状原因修法
模型绕着自己以外的地方转 围绕世界原点（0,0,0）旋转，而不是模型自身原点 把模型顶点挪到原点附近；或用「父节点当枢轴」
物体缩放后法线全错、光照发黑 直接用法线乘了模型矩阵，没处理非均匀缩放 用 UnityObjectToWorldNormal()；或先 normalize
手搓 MVP 后画面全黑 / 镜像 矩阵乘法顺序写反（M*V*P），或忘了转置 永远是 P * V * M；Unity 用列主序
屏幕 UV 上下颠倒，只在打包后出现 用 Screen.width / height 硬算，没考虑渲染到纹理时的 y 翻转 用 ComputeScreenPos()，它已经处理了平台差异
物体贴脸就消失 被近裁剪面裁掉了 近裁剪面从 0.01 调到 0.1/0.3（见第 02 章）

自测：三题

能答上来，这章就过关了。

自测 · 3 个问题（先自己答，再展开）
  1. transform.position 和 transform.localPosition 分别属于哪个空间？ position 是世界空间；localPosition 是相对父物体的局部空间。物体没有父物体时两者数值相同，但不代表它们是同一个概念。
  2. 为什么 Unity 的观察空间里相机朝 −Z，而世界空间里相机朝 +Z？ 因为 worldToCameraMatrix 在求逆时把 Z 轴翻转了一次，让观察空间符合 OpenGL 的右手系习惯（相机看向 −Z）。这是历史兼容，不是设计选择。
  3. 「物体在屏幕边缘被切掉一半」这件事，发生在哪个空间？ 裁剪空间。GPU 在透视除法之前、拿到齐次坐标时就做裁剪（判断 −w ≤ x,y,z ≤ w）。投影之后才做的就是光栅化了。
