第 02 章 · 摄像机

摄像机不是眼睛，是一道反向的数学

很多人学完坐标系统，还是说不清「摄像机到底做了什么」。答案很反直觉：摄像机永远不会移动，移动的是整个世界。视图矩阵就是把世界反向搬运的那个矩阵。这一章拆开它，顺便讲清 FOV、近裁剪面和视锥体。

一句话

视图矩阵 = 相机变换的逆。要得到「以相机为原点」的坐标，就乘它的逆矩阵。想通这一句，worldToCameraMatrix、LookAt、FOV、近裁剪面就全串起来了。

先破一个直觉

你说「相机往前走了一步」，从渲染的角度看，这等价于「整个世界往后挪了一步」。两种说法得到的画面完全一样。

为什么非要选后者？因为 GPU 光栅化时假定的坐标系是固定的：原点在相机、朝 −Z 看。它不会为你「移动眼睛」，它只会用固定的规则去投影一堆坐标。所以必须有人把世界搬到这个固定的位置上——那个人就是视图矩阵。

一个很好用的检查

把相机自己的位置用视图矩阵变换一次，结果必然是 (0, 0, 0)。因为「相机在相机空间里的位置」当然是原点。这个检查能瞬间验证你的矩阵有没有写错。

视锥体：相机能看见的那块空间

相机看到的不是一个无限空间，而是一个「四棱锥被切掉了尖」的形状——这就是视锥体（frustum）。它由四个参数决定：垂直视角 FOV、近裁剪面、远裁剪面、宽高比 Aspect。

什么时候不用透视

  • 2D 游戏：正交投影，物体永远一样大，不做近大远小。
  • 等距视角（Isometric）：正交 + 固定角度旋转，就是《暗黑破坏神》《模拟城市》那种。
  • UI / 小地图 / 后处理：正交，保证不出现透视畸变。
  • 阴影贴图：方向光的阴影通常用正交投影，因为「太阳的光线是平行的」（第 03 章会提到）。

视图矩阵，就是从「相机的角度」重新描述世界

相机的世界变换可以写成一个矩阵：先平移、再旋转，记作 T × R。视图矩阵就是它的逆：

公式

View = (T × R)−1 = R−1 × T−1

而「逆矩阵」的几何含义，正好就是把所有东西反向搬一次：相机在世界里往右挪 3 米，等价于世界往左挪 3 米。所以视图矩阵不需要任何「减去相机位置」的魔法，就是求逆。

C# 验证：视图矩阵就是相机变换的逆 
// 相机的世界变换矩阵
Matrix4x4 camTR = Matrix4x4.TRS(
    cam.transform.position,
    cam.transform.rotation,
    Vector3.one);

// 视图矩阵 = 它的逆
Matrix4x4 view = camTR.inverse;

// 检查：相机自己在观察空间里应该是原点
Vector3 camInView = view.MultiplyPoint3x4(cam.transform.position);
Debug.Log(camInView);   // ≈ (0.00, 0.00, 0.00)

// 检查：相机前方 5 米的点在观察空间里应该是 (0, 0, 5)？
// 注意！Unity 的观察空间相机朝 -Z，所以结果是 (0, 0, -5)
Vector3 ahead = cam.transform.position + cam.transform.forward * 5f;
Debug.Log(view.MultiplyPoint3x4(ahead));   // ≈ (0.00, 0.00, -5.00)

第二个检查特别值得注意：那个 −5 就是本章开头说的「观察空间是右手系」。如果你写 Shader 判断「物体在相机前面」，条件应该是 viewZ < 0，不是 > 0。

三根轴：forward、right、up 是怎么来的

相机的朝向不需要「角度」，只需要两根向量就能确定——因为第三根可以叉乘出来。这就是 LookAt 的全部原理：

  1. forward = normalize(target − position)　看向哪里
  2. right = normalize(cross(worldUp, forward))　用「世界上方」当参考
  3. up = cross(forward, right)　剩下那根自动补全

Unity 里不用手算

transform.LookAt(target) 一行就是上面三步。想连位置一起处理：Quaternion.LookRotation(target - pos, Vector3.up)。相机的三根轴可以直接读：transform.forward / .right / .up。

投影的三个参数：FOV、Near、Far

参数它在数学里是什么调大的后果调小的后果
Field of View 透视矩阵里的角度参数，垂直方向的视角 视野更广、边缘拉伸更严重、物体显小 画面像长焦镜头，纵深被压缩
Near 视锥体的前截面距离 深度精度变好，但贴脸的东西直接被裁掉 深度精度急剧变差 → z-fighting
Far 视锥体的后截面距离 能画更远，但深度精度被摊薄 远处物体凭空消失

FOV 是垂直的，不是水平的

Unity 的 Field of View 默认指垂直视角。同样 60° 的垂直 FOV，在 16:9 屏幕上水平视角约 91°，在 21:9 上约 106°。所以「同一个 FOV 在不同分辨率的手机上看到的范围不一样」——这就是为什么手游常把 FOV 按屏幕宽高比动态换算，而不是写死。

Near 不要设 0.01

深度缓冲的精度分布是极度不均匀的：靠近近裁剪面的地方精度极高，远处几乎为零。把 Near 从 0.3 调到 0.01，等于把几乎所有精度都浪费在眼前 10 厘米内，于是 20 米外的地面开始闪烁、贴花开始抖动。经验值：第一人称 0.05~0.1，第三人称 0.3，大场景 1 起步。

C# 第一人称相机：yaw 绕世界、pitch 绕自身 
using UnityEngine;

public class FPSCamera : MonoBehaviour
{
    public float sensitivity = 2.5f;
    public float moveSpeed   = 6f;

    float yaw, pitch;   // 分开存，避免从 eulerAngles 里读到 0~360 的怪值

    void Start()
    {
        Cursor.lockState = CursorLockMode.Locked;   // 锁鼠标，FPS 必做
        Cursor.visible   = false;
        yaw   = transform.eulerAngles.y;
        pitch = transform.eulerAngles.x;
    }

    void Update()
    {
        // 1) 看：yaw 绕世界 Y 轴，pitch 绕自身 X 轴
        yaw   += Input.GetAxis("Mouse X") * sensitivity;
        pitch -= Input.GetAxis("Mouse Y") * sensitivity;
        pitch  = Mathf.Clamp(pitch, -89f, 89f);     // 夹住，否则会翻跟头
        transform.rotation = Quaternion.Euler(pitch, yaw, 0f);

        // 2) 走：永远用相机自己的方向，而不是世界的 +Z
        float h = Input.GetAxis("Horizontal");
        float v = Input.GetAxis("Vertical");
        Vector3 dir = transform.right * h + transform.forward * v;
        transform.position += dir.normalized * (moveSpeed * Time.deltaTime);
    }
}

这里的第二段是关键：「前」是相机的 transform.forward，不是世界的 Vector3.forward。这就是局部空间和世界空间的区别落到实际代码上的样子。

C# 屏幕与世界互转（三个最常用的 API） 
// ① 3D 世界 → 屏幕像素。注意原点在左下角，y 轴向上
Vector3 screen = cam.WorldToScreenPoint(target.position);
bool inFront  = screen.z > 0f;   // z 是「距相机多远」，负数表示在相机背后

// ② 屏幕 → 射线（鼠标拾取、点击地面移动）
Ray ray = cam.ScreenPointToRay(Input.mousePosition);
if (Physics.Raycast(ray, out RaycastHit hit, 100f))
    Debug.Log("点到：" + hit.collider.name);

// ③ 屏幕 → 世界点。第三个参数不是「世界坐标 z」，而是「离相机多远」！
Vector3 world = cam.ScreenToWorldPoint(
    new Vector3(Input.mousePosition.x, Input.mousePosition.y, 5f));

第 ③ 条是全 Unity 最经典的误解

ScreenToWorldPoint 接收三个值，但只有两个是「屏幕」，第三个是相机空间里的深度。传 0 会得到相机自己所在的位置，传错误的值会得到看起来对、但永远偏的结果。要让物体贴地，正确做法是反过来用 ScreenPointToRay 打射线。

Shader 里的相机

  • _WorldSpaceCameraPos：相机的世界坐标，做高光、菲涅尔、雾都靠它。
  • UnityWorldSpaceViewDir(worldPos)：从某点指向相机的单位向量，就是 Blinn-Phong 里的 V。
  • UNITY_MATRIX_V：视图矩阵本体，需要手动转到观察空间时用。

Shader Graph 里对应 Camera 节点（Position / Direction / Near Plane / Far Plane）和一个现成的 View Direction 节点。

自测：三题

自测 · 3 个问题（先自己答，再展开）
  1. 相机往右移动 3 米，视图矩阵里的平移分量是 +3 还是 −3？ −3（方向上是把世界往左搬）。严格地说，视图矩阵是相机变换的逆，所以它的平移分量是「相机位置的负值再经过相机旋转」，不是简单的 −position。
  2. 把 FOV 从 60 调到 90，画面里同一个物体会变大还是变小？ 变小。FOV 越大，视锥体张得越开，同样的屏幕范围内塞进了更多东西，所以单个物体占比变小。这也是「广角让人显得小、长焦让人显得近」的原因。
  3. 为什么说 ScreenToWorldPoint 的第三个参数不是「世界的 z」？ 它是相机空间里的深度（距离相机多远）。屏幕坐标只有两个维度，缺少的正是深度，所以这个参数是在补第三个维度，而不是指定世界坐标的 z。
