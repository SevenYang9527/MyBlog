组件模式

用「有什么」代替「是什么」：把能力拆成可插拔的小块，运行时拼装，而不是靠继承树叉乘。

  • 25 分钟
  • 批次 1 · 引擎主干
  • GameObject · MonoBehaviour · RequireComponent · Prefab

原文在解决什么

如果按「类型」写继承，敌人一栏很快就会崩：Enemy 下面要分飞行 / 地面，再分近战 / 远程，再分有没有护盾——每加一个维度，类就翻一倍，最后出现 FlyingShieldedRangedEnemy。作者给的解法是分裂：GameObject 是空壳，Component 是能力切片，GameObject 只负责「持有」。

于是「飞行 + 护盾 + 远程」不是三个父类，而是三个部件。要新组合就换零件，不改类型系统。

Unity 里它长什么样

Unity 就是这个模式的成品实现，GameObject 天生没有行为，Transform 是唯一强制组件，其余全靠加。

// 不是 class FlyingEnemy : Enemy —— 而是拼装
[RequireComponent(typeof(Rigidbody2D))]
public class Flyer : MonoBehaviour
{
    [SerializeField] float thrust = 6f;
    Rigidbody2D rb;

    void Awake() => rb = GetComponent<Rigidbody2D>();
    void FixedUpdate() => rb.AddForce(Vector2.up * thrust);
}

// 敌人 = GameObject + Health + Flyer + Hitbox + Animator
// 加个 Boss 装甲？再挂一个 Armor —— 一行继承都不用动

拆分的边界是这章真正要学的东西，Unity 已经替你实现了模式，你得自己判断：

  • 能力拆成组件：移动、血量、攻击、掉落、视野。
  • 结构拆成子对象：模型、武器挂点、特效锚点、碰撞体。子对象跟着父级走，不该有独立逻辑。
  • 一个组件如果只能被一个对象使用，它其实就是「字段」，别硬拆。

什么时候别用

  • GetComponent 不是免费的，热路径（每帧几千次）必须缓存到字段。
  • 组件之间互发消息别用 SendMessage（反射、无法跳转、改名即崩），用接口 + 事件。
  • 拆得太碎会得到「二十个 20 行脚本，没人知道谁在驱动谁」——这时需要一个系统脚本（见更新方法）集中调度，而不是继续拆。
  • 必须同时存在的组件，用 [RequireComponent] 和预制体校验表达，而不是靠注释。

10 分钟动手

  1. 打开你项目里最大的那个 PlayerController.cs，数一下它现在的职责。
  2. 把「输入」「移动」「动画驱动」拆成三个组件，用事件或直接引用连起来。
  3. 删掉这个脚本，看 Inspector 里多出了多少引用——那就是你为解耦付出的可见成本。记下这个数字，下次判断「值不值得拆」时用它。
