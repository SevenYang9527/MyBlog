单例

一个类只允许一个实例，还给它开个全局入口。全书唯一一章劝你别用——而 Unity 新手最爱用。

  • 15 分钟
  • 批次 3 · 按需查
  • static Instance · DontDestroyOnLoad · RuntimeInitializeOnLoadMethod

原文在解决什么

有些东西客观上只该有一个：文件系统、日志、音频设备、配置。单例保证「唯一」，并提供全局访问点。

作者的结论是全书最直白的一句：这是最不推荐的模式，因为全局可变状态会让依赖不可见、测试变难、初始化顺序难以推理。他用了一整节讲「什么时候不要用」——那才是这章的价值。

Unity 里它长什么样

Unity 里最常见的写法（也是坑最多的）：

public class GameManager : MonoBehaviour
{
    public static GameManager Instance { get; private set; }

    void Awake()
    {
        if (Instance != null && Instance != this)
        {
            Destroy(gameObject);       // 场景里挂了两个
            return;
        }
        Instance = this;
        DontDestroyOnLoad(gameObject);
    }

    void OnDestroy()
    {
        if (Instance == this) Instance = null;   // 别漏，否则退出播放模式后残留引用
    }
}

Unity 特有的三个坑：

  • 编辑器域重载：不写 OnDestroy 里的置空，停止播放后 Instance 仍指向已销毁对象。
  • 场景叠加：DontDestroyOnLoad + 每个场景都放一份 = 两份共存，靠上面的 Destroy 救场。
  • 静态状态：静态字段在编辑器里跨播放会话残留（Domain Reload 被关闭时尤其明显）。

什么时候别用

按优先级选替代方案：

  1. 只读配置 → ScriptableObject 资产（数据不需要「管理」）。
  2. 每个场景一个的自然单例 → 场景内 [SerializeField] 引用，谁需要谁拖。
  3. 纯函数工具 → static class（无状态，没有「唯一实例」问题）。
  4. 真的全局服务 → DI 容器（VContainer）管理生命周期。
  5. 最后才是单例，并且只读、无状态、可重置。

10 分钟动手

  1. 全局搜 Instance，数一下有多少个 Manager.Instance。
  2. 挑一个，问三个问题：它需要「唯一」吗？它需要「全局访问」吗？它是只读的吗？
  3. 三个都「是」→ 留着。有一个「否」→ 按上面的顺序换掉一个。
