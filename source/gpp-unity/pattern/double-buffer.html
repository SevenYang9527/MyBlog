双缓冲

读写同一份数据，读者会看到「改到一半」的中间态。两份数据 + 交换，让读者永远看到完整的一帧。

  • 20 分钟
  • 批次 3 · 按需查
  • 输入快照 · 回滚网络 · 录像回放

原文在解决什么

渲染时，如果直接在正在显示的那块显存上画，观众会看到画了一半的画面（撕裂）。经典解法：画在另一块内存上，画完整帧再交换指针。

推广开来：任何「写者持续修改、读者需要一致快照」的场景都用得上。交换之所以几乎免费，是因为换的是指针，不是数据。

Unity 里它长什么样

帧缓冲与渲染管线由引擎负责，你碰不到。你能用到它的地方是「逻辑层」：

public struct InputFrame
{
    public float moveX, moveY;
    public bool jump;
    public int tick;
}

InputFrame[] buffers = { new InputFrame(), new InputFrame() };
int cur;                              // 当前「已确认」的那一份

void RecordTick(InputFrame input)
{
    int next = 1 - cur;
    buffers[next] = input;            // 只写不读的那一份
    cur = next;                       // 交换
}

三个真实场景：

  • 输入快照：网络同步里「上一帧输入」用于插值/外推，必须保留完整一份。
  • 回滚网络（GGPO 式锁步）：保存最近 N 帧状态，收到旧输入就回滚重算——这其实是「多缓冲」。
  • 录像 / 回放：录制时写缓冲，播放时读缓冲，互不干扰。

什么时候别用

  • 只在「读者与写者跨帧」时才需要。同一帧内的读写，用队列或脏标记更简单。
  • 双缓冲会延迟一帧：1 - cur 意味着读者看到的永远是上一帧。对输入响应敏感的逻辑要意识到这个延迟。
  • 三缓冲 / 环形缓冲才是录制的正解：双缓冲只能存一帧，回滚需要历史。

10 分钟动手

  1. 写一个「录制 60 帧输入 + 完整回放」的小程序，用两个 InputFrame 数组交替写。
  2. 把回放时的位置和录制时对比，确认逐帧一致。
  3. 额外思考：如果要回滚 5 帧，你的结构要怎么改？（提示：环形缓冲）
