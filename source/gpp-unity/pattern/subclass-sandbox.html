子类沙箱

基类提供一小盒「积木」，子类只准用这些积木搭东西，不许直接碰引擎全局 API。

  • 20 分钟
  • 批次 2 · 架构升级
  • 基类 protected 辅助方法 · 模板方法 · 受控 API 面

原文在解决什么

当一堆子类都要做相似的事（播放特效、生成物体、加伤害），它们会各自去调引擎 API。结果是重复代码 + 全局依赖散落各处。沙箱的做法：基类暴露一组 protected 的语义化方法（Spawn、PlayFx、DealDamage），子类只组合这些方法。

两个收益：子类变短；将来换实现（换特效系统、加埋点）只改基类。

Unity 里它长什么样

其实 MonoBehaviour 本身就是一个巨大的沙箱：生命周期方法 + transform + GetComponent，你从没直接碰过引擎内部。

自己再包一层，通常长这样：

public abstract class AbilityBase : MonoBehaviour
{
    protected void Spawn(GameObject prefab, Vector3 at)
        => Instantiate(prefab, at, Quaternion.identity);

    protected void Damage(IDamageable target, int amount)
    {
        if (target == null) return;
        target.TakeDamage(amount);
        Analytics.Track("damage", amount);   // 统一埋点，子类不用管
    }

    protected void PlayFx(string key) => Fx.Play(key, transform.position);

    public abstract void Cast();
}

public class Fireball : AbilityBase
{
    [SerializeField] GameObject ball;
    public override void Cast()
    {
        Spawn(ball, transform.position + transform.forward);
        PlayFx("cast_fire");
    }
}

什么时候别用

  • 沙箱会腐化：一开始 5 个方法，两个月后 40 个，最后变成一个没人敢改的上帝基类。约束是「只放这一类子类都会用的操作」，且方法要语义化（DealDamage 而不是 GetComponent().Set(...)）。
  • 只有 2 个子类时，沙箱是过度设计。
  • 如果子类需要的能力差异很大，说明它们不该共享这个基类——回到组件模式。

10 分钟动手

  1. 找 3 个技能脚本，看它们重复了哪些 Instantiate / GetComponent / PlayEffect。
  2. 上移到基类，子类只留「数值 + 调用顺序」。
  3. 删掉一个子类，看基类是否需要跟着改——如果不用改，说明边界划对了。
