服务定位器

一个全局的「找服务」入口。比单例灵活，但依赖仍是隐式的——所以它只是「较不坏」。

  • 20 分钟
  • 批次 2 · 架构升级
  • 静态注册表 · VContainer / Zenject · SerializeField 注入

原文在解决什么

有些服务（音频、存档、对象池、网络）被到处用，靠构造函数一路传下去太啰嗦。服务定位器提供一个全局查表：谁需要谁自己去取。

它和单例的区别：单例是「这个类只有一个」，服务定位器是「这类服务有一个实现」，实现可以换（真机 / 编辑器 / 测试）。

作者的态度很明确：它比单例好，但仍然不如显式依赖，因为看一个类的构造函数，你不知道它到底依赖了什么。

Unity 里它长什么样

public static class Services
{
    static readonly Dictionary<Type, object> map = new();

    public static void Register<T>(T impl) => map[typeof(T)] = impl;
    public static T Get<T>() => (T)map[typeof(T)];
    public static bool TryGet<T>(out T impl)
    {
        if (map.TryGetValue(typeof(T), out var o)) { impl = (T)o; return true; }
        impl = default; return false;
    }
}

// 启动时注册
Services.Register<IAudio>(new AudioService());
// 任意位置取用
Services.Get<IAudio>().Play("hit");

Unity 生态里更常见的两条路：

  • SerializeField 注入：最土，但依赖在 Inspector 里看得见，适合中小项目。
  • DI 容器（VContainer / Zenject）：构造注入 + 生命周期管理，大项目值得，学习成本真实存在。

什么时候别用

  • 依赖不可见 = 测试要预置一堆注册，新人接手不知道从哪开始。
  • 注册顺序会变成隐式依赖：Get() 在 Awake 里调用，但注册在 Start 里——空引用。
  • 优先顺序：序列化引用 > 构造函数/DI 注入 > 服务定位器 > 单例 > 静态类。

10 分钟动手

  1. 全局搜 FindObjectOfType，找出 3 处。
  2. 其中两处改成 [SerializeField] 显式引用，一处保留并加注释说明为什么。
  3. 体会差别：显式引用在场景里一眼能看出依赖，Find 不能。
