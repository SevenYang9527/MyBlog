原型

与其「创建一个全新的」，不如「复制一个现成的」。克隆自带所有配置，比重新装配便宜。

  • 10 分钟
  • 批次 3 · 按需查
  • Instantiate(prefab) · Prefab Variant · 运行时副本

原文在解决什么

怪的生成器如果每次都要 new Monster() 再逐项赋值，就得知道所有字段——而且改一个字段要改所有生成器。原型模式反过来：先做一个配置好的样本（原型），需要时克隆它。

好处：创建逻辑集中在一处（原型本身），生成器完全不关心数据细节。作者也提醒了深浅拷贝的坑：引用字段会被共享。

Unity 里它长什么样

Prefab 就是这个模式的工业化实现，你几乎不需要自己写 Clone：

// 预制体 = 原型；Instantiate = 复制
var enemy = Instantiate(enemyPrefab, spawnPos, Quaternion.identity);

// 值类型字段被复制；引用字段（如 List、脚本引用）是浅拷贝，指向同一个对象
// 想独立，用完立刻复制那份引用数据
enemy.GetComponent<LootTable>().Rolls = new List<Roll>(template.Rolls);

Unity 还给了两个原型变体：

  • Prefab Variant：从另一个预制体派生，改一处不影响父级，保留继承关系（改父级会传递到未覆盖的字段）。
  • ScriptableObject 副本：运行时要改配置时先 Instantiate(so)，避免污染磁盘资产。

什么时候别用

  • 创建逻辑其实很轻、字段很少时，工厂方法更清楚，克隆反而让人不知道对象从哪来。
  • 浅拷贝是主要事故源：克隆后改一个 List 元素，原型和所有克隆一起变。
  • 别用 Instantiate 做「带副作用」的初始化——它会连 Awake 一起跑，顺序难以预料。

10 分钟动手

  1. 写一个 List 字段的组件，挂在预制体上。
  2. Instantiate 三份，改其中一份的 List，看另外两份是否被改。
  3. 这个问题真实存在，且只在运行时暴露——花 10 分钟认它一次，值。
