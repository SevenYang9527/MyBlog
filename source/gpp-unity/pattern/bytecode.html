字节码

用数据描述行为，让一个小解释器去执行。灵活到能热更，但也把调试难度一起买了回来。

  • 25 分钟
  • 批次 3 · 按需查
  • SO 技能配置 · Visual Scripting · Lua 热更

原文在解决什么

硬编码的行为改一次要编译一次；如果行为本身是内容（技能、关卡逻辑、对话），就希望它变成数据。字节码是这条路线的标准答案：定义一组指令 + 一个栈/寄存器解释器，行为写成指令序列。

作者的态度很谨慎：只有当内容复杂度超过代码复杂度时才值得，而且必须配套工具与调试手段。

Unity 里它长什么样

三个层级，从轻到重：

  1. ScriptableObject + 指令列表（最轻，多数项目够用）：
public enum Op { Damage, Heal, SpawnFx, Delay, Repeat }

[System.Serializable]
public struct Instr
{
    public Op op;
    public int amount;
    public float wait;
}

[CreateAssetMenu(menuName = "GPP/Skill")]
public class Skill : ScriptableObject
{
    public string displayName;
    public List<Instr> instructions = new();
}

// 解释器：几十行就能跑
public IEnumerator Run(Skill skill, IDamageable target)
{
    foreach (var i in skill.instructions)
    {
        switch (i.op)
        {
            case Op.Damage: target.TakeDamage(i.amount); break;
            case Op.Heal:   /* ... */ break;
            case Op.Delay:  yield return new WaitForSeconds(i.wait); break;
        }
    }
}
  1. 可视化脚本（Visual Scripting / Playmaker）：本质也是字节码，只是编辑器更好用。
  2. 脚本语言热更（Lua / HybridCLR）：需要热更能力时才上，运维成本真实。

Unity 内部也在用：Animator 的状态机运行时就是字节码，Timeline 的轨道也是数据驱动执行。

什么时候别用

  • 只为了「策划能改技能」就上字节码 → 先试试把参数抽成 SO（组合优于解释）。
  • 解释器没有栈信息，报错只会告诉你「第 37 条指令崩了」，排查成本远高于普通代码。
  • 性能敏感的逻辑别走解释执行，尤其每帧调用的。
  • 一定要配可视化编辑器或至少文本格式（可 diff、可代码评审），否则维护会失控。

10 分钟动手

  1. 用 6 条指令实现「火球术：立即伤害 → 等 0.3s → 生成特效 → 再伤害一次」。
  2. 在 Inspector 里改数值，不重编译。
  3. 给解释器加一行「当前执行到第几条」的日志——这就是它的断点。
