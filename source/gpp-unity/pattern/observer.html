观察者

让「发生了什么」和「谁关心」互不认识。代价是控制流消失，出问题只能靠日志回溯。

  • 25 分钟
  • 批次 1 · 引擎主干
  • event / Action · UnityEvent · SO 事件通道

原文在解决什么

成就系统要关心「敌人死亡」，UI 要关心「血量变化」，音效要关心「受击」。如果每处都直接引用，Player 就会认识所有人，改一个 UI 就要动核心类。

观察者把它倒过来：发布者只喊一声，订阅者自己决定听不听。发布者不知道订阅者是谁、有几个、是否还活着。

Unity 里它长什么样

三档，按「要不要给策划连」选：

// 1) C# event：最快，纯代码
public class Health : MonoBehaviour
{
    public event Action<int> Changed;
    public event Action Died;
    int hp = 100;

    public void TakeDamage(int dmg)
    {
        hp -= dmg;
        Changed?.Invoke(hp);
        if (hp <= 0) Died?.Invoke();
    }
}

// 2) 订阅方必须成对退订，否则场景重载后旧对象还在被引用
public class HealthBar : MonoBehaviour
{
    [SerializeField] Health health;
    void OnEnable()  => health.Died += Hide;
    void OnDisable() => health.Died -= Hide;
}
  1. UnityEvent：Inspector 里能拖引用、能选方法，策划友好，但调用慢、改名易断，且不适合高频事件（如每帧血量）。

还有一种 Unity 特有的漂亮做法：ScriptableObject 事件通道——把事件本身做成资产，发布者与订阅者都只引用这个资产，两个场景/两个预制体之间零直接引用。

什么时候别用

  • 静态事件是内存泄漏头号来源：场景切换后旧对象仍挂在静态 event 上。一定要在 OnDisable 退订，或改用 ScriptableObject 通道。
  • 事件链超过三层（A→B→C→D）就画不出调用栈了，这时该用显式调用或消息队列。
  • 高频事件（每帧、每颗子弹）别用 UnityEvent。
  • 留一份事件日志：Debug.Log 或自建环形缓冲，出 bug 时能倒推「谁触发的」。

10 分钟动手

  1. 把 UI 里「直接引用玩家脚本读血量」改成订阅事件。
  2. 故意删掉 OnDisable 里的退订，重载场景，观察 MissingReferenceException。
  3. 加回退订，再测一次。这个报错你以后一定还会遇到，先认识它。
