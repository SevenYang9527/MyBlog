游戏循环

游戏不等人输入，它自己一直在跑。循环用哪种步长，决定了物理稳不稳、表现顺不顺。

  • 25 分钟
  • 批次 1 · 引擎主干
  • Update · FixedUpdate · Time.deltaTime · targetFrameRate

原文在解决什么

网页是「事件驱动」：没有点击就不做事。游戏相反，它必须每帧主动推进世界。while (true) 里做三件事：读输入 → 更新状态 → 渲染。

关键分歧在「更新」的步长：

  • 可变步长：dt 随帧率变化。简单，但同一段物理在不同帧率下结果不同，高速物体会穿墙。
  • 固定步长：每次推进固定时间（如 1/60 s），帧率不够就一帧跑多次。物理稳定可复现，代价是表现可能「跳」。

Unity 里它长什么样

引擎已经写好循环（PlayerLoop），你只挂上去。三个入口的分工必须记牢：

void FixedUpdate()  // 默认 50Hz 固定步长，物理、刚体、射线检测放这里
void Update()       // 每帧一次，可变 dt。输入、动画、游戏逻辑
void LateUpdate()   // 所有 Update 之后，相机跟随、IK 修正

// 与帧率无关的移动
void Update() => transform.Translate(Vector3.forward * speed * Time.deltaTime);

Time.fixedDeltaTime 是物理步长（默认 0.02），Time.deltaTime 是上一帧耗时。改 Time.timeScale = 0.2f 会同时缩放两者，但物理步长不变，只是 FixedUpdate 被调用的次数变少——所以慢动作下物理精度会下降。

什么时候别用

  • 别在 FixedUpdate 里读 Input：它一帧可能执行 0 次或多次，输入会丢。
  • 别用 Time.deltaTime 驱动 Rigidbody：物理已经在固定步长里积分，再乘 dt 就重复了。
  • Application.targetFrameRate 在移动端要和垂直同步一起考虑，别设成不存在的值。
  • 需要「暂停」时改 timeScale，但注意用 unscaledDeltaTime 的 UI 动画不受影响。

10 分钟动手

  1. 在 Update 里打印 Time.deltaTime，把帧率锁到 30 再放开，看数值怎么跳。
  2. 写一个匀速移动的方块：先用 Update + deltaTime，再用 FixedUpdate + fixedDeltaTime，把帧率压到 20 观察差异。
  3. 用 Physics.Raycast 在 Update 里检测一次，再挪到 FixedUpdate，体会「一帧多次检测」的后果。
