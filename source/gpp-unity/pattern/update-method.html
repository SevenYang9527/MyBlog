更新方法

让每个对象知道怎么更新自己——好写，但每帧的调度成本会随对象数线性堆起来。

  • 20 分钟
  • 批次 1 · 引擎主干
  • MonoBehaviour 生命周期 · 协程 · 集中式系统

原文在解决什么

最直觉的做法：每个实体一个 Update()，世界维护一个列表，每帧遍历调用。对象内部封装自己的行为，主循环完全不知道细节——非常干净。

代价在遍历本身：虚拟调用、缓存不友好、顺序不可控。作者给了两个升级方向：集中式（一个系统遍历数据，对象退化成纯数据）和分片更新（不同对象不同频率，远处敌人每 5 帧算一次）。

Unity 里它长什么样

MonoBehaviour 的 Update 就是引擎替你维护的对象列表——但每次调用都要从原生跨到托管，一万个对象就是一万次跨界。

// A：对象自己更新（默认写法，几百个以内很舒服）
public class Bullet : MonoBehaviour
{
    public float speed = 12f;
    void Update() => transform.position += transform.forward * speed * Time.deltaTime;
}

// B：集中更新（上千个单位时明显更省）
public class BulletSystem : MonoBehaviour
{
    readonly List<BulletData> bullets = new();
    void Update()
    {
        float dt = Time.deltaTime;
        for (int i = bullets.Count - 1; i >= 0; i--)
            bullets[i].Tick(dt);          // 纯 C# 结构，不进 PlayerLoop
    }
}

B 的额外好处：可以统一暂停、统一排序、批量处理、方便对象池回收。代价是失去 Inspector 可视化、OnEnable 语义和「拖进去就能跑」的便利。

什么时候别用

  • 对象数在几百以内，别急着集中化，Update 的可读性值这个钱。
  • 别用「每帧 FindObjectsOfType 再更新」——那是把成本翻十倍。
  • 别在 Update 里创建临时 List/闭包：GC Alloc 会在 Profiler 里一路飘红。
  • 真正上万的规模，答案是 DOTS / ECS（数据局部性那章），不是自己手写循环。

10 分钟动手

  1. 生成 2000 个会移动的 Cube，各自 Update，Profiler 记下 BehaviourUpdate 耗时。
  2. 改成「一个系统遍历 Transform 数组」，再记一次。
  3. 把差距写进笔记——这是你以后判断「要不要集中更新」的基准。
