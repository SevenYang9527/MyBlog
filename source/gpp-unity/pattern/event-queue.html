事件队列

别在事件发生的瞬间处理它：先入队，在安全的时机统一消费，顺序与重入都可控。

  • 25 分钟
  • 批次 2 · 架构升级
  • 消息队列 · 单帧延迟 · CommandBuffer

原文在解决什么

直接回调有两个麻烦：重入（A 触发 B，B 又改 A 的列表，正在遍历的集合被修改）和时序（「死亡 → 掉宝 → UI → 音效」的先后由调用顺序决定，改动一处就乱）。

队列化把「发生」和「处理」拆开：发布只是入队，消费发生在循环的固定位置，一次处理一批。

Unity 里它长什么样

Unity 没有内置通用事件队列，但到处都是它的影子：CommandBuffer（渲染指令排队）、NetworkClient 的消息队列、Addressables 的回调队列。

自己实现一个最小的：

public static class GameEvents
{
    static readonly Queue<Action> queue = new(64);

    public static void Push(Action e) => queue.Enqueue(e);

    // 在某个系统的 Update 末尾调用一次
    public static void Flush()
    {
        int count = queue.Count;          // 只消费这一帧入队的，避免死循环
        while (count-- > 0 && queue.Count > 0)
            queue.Dequeue()?.Invoke();
    }
}

用法：GameEvents.Push(() => OnEnemyDied(enemy));。好处是「死亡处理」永远发生在帧末，遍历中途不会被打断。

进阶：队列可以合并（同一目标的多段伤害累加后只处理一次）、排序（优先级队列）、跨帧（延迟到下一帧生效，做「回合结算」很自然）。

什么时候别用

  • 语义会变：本来「立刻发生」的事变成「这帧末/下一帧发生」。跨帧队列尤其危险，动画和表现会晚一帧。
  • 调试变难：调用栈里看不到「谁触发的」，必须记事件日志。
  • 每帧几百个事件时，Action 闭包会产生 GC Alloc，改用结构体事件 + 泛型队列。

10 分钟动手

  1. 找出项目里「在一个 foreach 里删元素」的代码，那通常就是重入 bug 的现场。
  2. 把「死亡 → 掉落 → 加分 → 音效」改成入队，在 LateUpdate 里 Flush。
  3. 故意在 Flush 里再 Push 一个事件，确认你的实现不会无限循环。
